# Django

ormbridge reads and writes Django models (`ormbridge formats` lists `django` as `read + write`). Reading is static: the Python in `models.py` is parsed with tree-sitter, so no Python, Django install or database is needed. Writing produces one `models.py` text. The format claims the `.py` extension, so `--from django` / `--to django` can usually be left out when the input or output ends in `.py`. Pass the flag explicitly when reading a directory (a directory never infers the format), and use `--from sqlalchemy` or `--to graphene` for other Python formats.

If neither `--from` nor an inferable extension is given, the source defaults to `django`. The target defaults to `prisma` when reading Django and to `django` otherwise.

## Try it

The example in [`examples/django`](../../examples/django/) holds two conversions in its `ormbridge.config.json`:

```bash
cd examples/django
npx ormbridge convert            # runs both conversions
npx ormbridge convert --check    # exits 3 if a generated file is stale
```

| Conversion    | Input                     | Output                 |
| ------------- | ------------------------- | ---------------------- |
| `to-django`   | `../schema/schema.prisma` | `models/models.py`     |
| `from-django` | `models` (the folder)     | `prisma/schema.prisma` |

Inside this repository run `node ../../dist/cli.js convert` after `npm run build`. Without a config file the same conversions are `ormbridge convert -i schema.prisma -o models.py` and `ormbridge convert -i ./models -f django -o schema.prisma`.

## Reading

- **Input.** A `models.py` file, a `models/` package (every `.py` except `__init__.py`), or a directory that is searched for both. Several files are merged into one schema, so an abstract base class can live in another file. Directory walks skip `migrations`, `node_modules`, `venv`, `.venv`, `env`, `.git`, `__pycache__`, `site-packages`, `dist` and `build`. A file passed explicitly is always read.
- **Models.** Classes that inherit `models.Model`, directly or through abstract bases and mixins. `abstract = True` classes are not models. Proxy models are merged into their concrete model; multi-table inheritance becomes a one-to-one primary key (each case warns).
- **Fields.** Scalar field classes (`CharField`, `TextField`, the integer, `DecimalField`, `BooleanField`, date/time, `UUIDField`, `JSONField`, `BinaryField`, IP, `DurationField` families), PostgreSQL `ArrayField`, `HStoreField` and range fields, and `GeneratedField`. Options read include `null`, `unique`, `primary_key`, `max_length`, `max_digits`, `decimal_places`, `db_column`, `default` (literals, `timezone.now`, `uuid.uuid4`, `dict`/`list`), `db_default`, `auto_now` and `auto_now_add`.
- **Enums.** `TextChoices` classes and inline `choices=[(value, label), ...]` become enums with labels.
- **Relations.** `ForeignKey`, `OneToOneField` and `ManyToManyField`, with `on_delete` and `related_name`. A `ManyToManyField` with `through=` is skipped because the explicit through model carries the relations.
- **Meta.** `db_table`, `unique_together`, `index_together`, `indexes`, `UniqueConstraint` and `CompositePrimaryKey` (Django 5.2).
- **Table names.** A model without `db_table` gets `<app_label>_<model>`. The app label is the directory that holds `models.py` (or the parent of `models/`); `--app-label <name>` overrides it. `--auto-field int|bigint` sets the key type of models that declare no primary key (default `int`).

## Writing

The emitter returns a single text that starts with `# Generated by ormbridge. Review the output before running migrations.` It writes:

- `models.TextChoices` classes for enums, and `choices=<Enum>.choices` on the column. The column is `CharField(max_length=N)` with `N` the longer of 32 and the longest value.
- `Meta.db_table`, `models.UniqueConstraint` and `models.Index` entries; index names longer than 30 characters are shortened.
- `ForeignKey`, `OneToOneField` and `ManyToManyField` with `related_name`. `onDelete` maps to `CASCADE`, `SET_NULL`, `PROTECT` (Restrict), `DO_NOTHING` (NoAction) or `SET_DEFAULT`.
- `models.AutoField(primary_key=True)` for auto-increment keys.

The Django writer takes no options (to run the models on CockroachDB, install `django-cockroachdb` for your Django version and set `'ENGINE': 'django_cockroachdb'`; the writer does not check it): `--naming`, `--provider`, `--no-header` and the other writer flags have no effect on Django output. Table names always come through `Meta.db_table` (for example `blog_post`).

## Limitations and warnings

Warnings go to stderr as `warning: ...` and name the model and field. Examples that the Django reader or writer emits:

- `Post.author: settings.AUTH_USER_MODEL was assumed to be a model named "User".` Models referenced but not found get a stub with an auto-increment id.
- `<file>: Post.Meta: CheckConstraint(...) could not be converted (only field-based indexes and unique constraints are supported).` `UniqueConstraint(condition=...)`, `GenericForeignKey` and `GenericRelation` are skipped too.
- `<Model>.<field>: unknown field type "X"; it was converted as a plain string column. Review the generated type.`
- Writer: `models.GeneratedField requires Django 5.0 or newer`, `db_default requires Django 5.0 or newer`, the `CompositePrimaryKey` warning (Django 5.2), and `onDelete SetNull requires a nullable relation in Django; it was converted to PROTECT.`
- Prisma-only constructs (views, `Unsupported(...)` columns, `@@fulltext`, composite foreign keys, `cuid()` defaults) have no Django equivalent and warn, for example `Place.slug: the cuid() default is generated by Prisma Client and was dropped.`

Python is parsed statically: computed defaults, custom field classes and fields added dynamically are skipped or approximated. `GeneratedField` expressions survive only into Django output. Array, HStore and range fields only work on PostgreSQL.

What survives a round trip is in the [conversion matrix](../CONVERSION_MATRIX.md): [django to prisma](../CONVERSION_MATRIX.md#django--prisma), [prisma to django](../CONVERSION_MATRIX.md#prisma--django), [django to typeorm](../CONVERSION_MATRIX.md#django--typeorm) and [django to doctrine](../CONVERSION_MATRIX.md#django--doctrine). The usual losses (enum column length and member labels, many-to-many fields becoming an explicit join model in Prisma) are listed under [why information is lost](../CONVERSION_MATRIX.md#why-information-is-lost).

## Programmatic API

```ts
import {
  convertText,
  parseDjango,
  type ConvertResult,
  type IrSchema,
  type Result,
} from 'ormbridge';

declare const prismaText: string;
declare const modelsPy: string;

// Prisma -> Django, in memory.
const converted: Result<ConvertResult> = await convertText(
  [{ path: 'schema.prisma', text: prismaText }],
  {
    from: 'prisma',
    to: 'django',
    naming: 'preserve',
    provider: 'postgresql',
    header: true,
    autoField: 'int',
  }
);
if (converted.ok) {
  console.log(converted.value.output); // models.py text
  console.warn(converted.value.warnings);
} else {
  console.error(`${converted.error.code}: ${converted.error.message}`);
}

// Read Django into the shared model.
const parsed: Result<IrSchema> = await parseDjango(
  [{ path: 'shop/models.py', text: modelsPy, appLabel: 'shop' }],
  { autoField: 'int' } // 'int' | 'bigInt' (the CLI spells it bigint)
);
```

`emitDjango(schema)` returns `{ text, warnings }` directly (it is not a `Result`); `convertText` wraps it.
