## Limitations and warnings

ormbridge never fails silently on something it cannot represent: each case produces a `warning:` on stderr naming the model and field. The main ones:

- `settings.AUTH_USER_MODEL` and `get_user_model()` are assumed to be a model named `User`. Models referenced but not found in the input get a stub with an auto-increment id.
- `GeneratedField` expressions are Python (`F`, `Concat`, ...), so they are carried only into Django output; Prisma and TypeORM get a regular column and a warning. Range fields are `Unsupported(...)` in Prisma and `string` in TypeORM and TypeScript objects (`{ lower, upper, bounds }`), nested arrays are `Json` in Prisma, `size=` on `ArrayField` is not kept, and `FileField` / `ImageField` / `FilePathField` / `GenericIPAddressField(protocol=...)` options are not kept (they come back as `CharField` or a plain IP field). `UniqueConstraint(condition=...)` (partial unique constraints), `GenericForeignKey` / `GenericRelation` and `CheckConstraint` are skipped with a warning.
- Python is parsed statically, so computed defaults, custom field classes, and fields added dynamically are skipped or approximated.
- Prisma composite primary keys become `models.CompositePrimaryKey` (Django 5.2+). Composite foreign keys, `Unsupported(...)` types, views, `@@fulltext`, `@@schema`, `@ignore` and client-generated defaults (`cuid()`, `ulid()`, `nanoid()`) have no direct Django, TypeORM, TypeScript or Graphene equivalent (except that TypeORM writes a view as a `@ViewEntity`, see below); the composite key columns stay as plain fields, a view becomes a table in Django, TypeScript and Graphene, and each case warns. Scalar lists become `ArrayField` (PostgreSQL only).
- Not read from Prisma schemas: composite types (`type` blocks, MongoDB), `relationMode`, the client-side `name:` of `@@unique` / `@@id`, partial indexes (`where:`), `@default(..., map:)` constraint names (SQL Server), and sort / length options on `@@id`. Native types are matched to the target provider by name only (the table was built with `prisma validate`); arguments such as a `VarChar` length are passed through unchanged. MongoDB output warns about ids that are not `@map("_id") @db.ObjectId` and about `Decimal` and compound ids, which Prisma rejects there. SQL Server cannot index `NVarChar(Max)` and MySQL needs a prefix length to index `TEXT`; indexes on such columns warn.
- Prisma's implicit many-to-many join table (`_AToB`) differs from Django's, so data needs migrating.
- TypeORM: entities are read from decorators only. Not supported, each with a warning naming the entity and column: `EntitySchema`, `@ChildEntity` / `@TableInheritance` (single-table inheritance), `@Tree*`, `@ObjectIdColumn`, `@VirtualColumn`, array columns, partial and spatial indexes, `@Check` / `@Exclusion`, composite foreign keys, relations inside embedded entities, and column options such as `unsigned`, `collation` and `transformer`. `@ViewEntity` classes are read as views (`isView`) with their `@ViewColumn` columns; the view's `expression` is not converted. A Prisma view is written as `@ViewEntity({ name, expression })` with `@ViewColumn()` columns and a placeholder `expression` (`SELECT * FROM <view>`, which selects from the view itself) plus a TODO comment and a warning: replace it with the query that defines the view, because a Prisma schema carries no view definition. Primary key, unique and index information on a view is dropped. Custom `@JoinTable` names are not preserved. Relations without `onDelete` become `NoAction` and relations are nullable unless `nullable: false`, as in TypeORM. Numeric enums become integers.
- TypeORM many-to-many relations use TypeORM's join table (composite key), so Django's surrogate `id` column on the join table is not reproduced. SQL Server has no enum column, so enums become `varchar`. Database-side UUID defaults are not available on SQLite. MongoDB entities are not supported.
- Doctrine: only PHP 8 attributes are read. Docblock annotations (`@ORM\Entity`) are detected and reported with a warning (or an error when nothing else is found), and XML / YAML mappings are not read; both are planned. Lifecycle callbacks other than a plain timestamp assignment, and constructor or initializer values that need to run PHP (method calls, constants other than enum cases), are ignored with a warning. Not supported, each with a warning naming the entity and property: attribute and association overrides, composite foreign keys (several `#[ORM\JoinColumn]`), `columnDefinition`, `unsigned` / `comment` / `collation` and other column `options`, `insertable: false` / `updatable: false`, partial and spatial indexes, table `schema` and `options`, custom id generators and `#[ORM\SequenceGenerator]`, `array` / `object` / `simple_array` / custom DBAL types, int-backed and non-backed enums, relations inside embeddables, and the `#[ORM\DiscriminatorMap]` values (the discriminator column is kept, the map is not). Nullability follows the attribute (`nullable: true`), never the PHP type: Doctrine does not infer it, so `?string` with a plain `#[ORM\Column]` is `NOT NULL`. Custom join table names, ORM-level `cascade` / `fetch` / `orphanRemoval` and other runtime-only settings are not part of the schema and are not converted; `cascade: ['remove']` and `orphanRemoval` warn. A custom naming strategy configured outside the attributes cannot be seen, so Doctrine's underscore naming is assumed. Classes the input does not contain (a vendor base class or trait, an enum in another package) produce a warning that names the missing class.
- Laravel: the schema is rebuilt statically, so what Laravel decides at run time is not seen. A conditional or loop inside a migration is applied as if it always ran, and a dynamic table or column name is skipped; both warn and name the table. Raw SQL (`DB::statement`, `DB::unprepared`) is not interpreted, so a view, trigger, partial index or column created that way is missing, with a warning naming the table. Not represented, each with a warning naming the table and column: polymorphic relations (`morphs`, `morphTo`, `morphMany`, `morphToMany`; the `_type` and `_id` columns stay plain columns), derived relations (`hasManyThrough`, `hasOneThrough`, `*OfMany`), relation constraints (`->where(...)`), composite foreign keys, foreign keys to tables no migration creates, tables that migrations alter but never create (for example `users` from a package), `set`, geometry and `vector` columns, `macAddress` (kept as a string), identity columns, spatial indexes, custom pivot table and key names (the join table gets the name other formats derive: `blog_post_tags` survives, `post_tag` does not), pivot timestamps and non-cascading pivot keys, and `parentKey` / `relatedKey` that are not the primary key. Casts to custom cast classes and to int-backed enums are ignored. Mass-assignment and visibility properties (`$fillable`, `$guarded`, `$hidden`) are not part of the schema. Soft deletes have no IR equivalent beyond the nullable `deleted_at` column.
- GORM: only struct tags are read and nothing is executed, so a `TableName()` that computes its result, a custom `NamingStrategy` (prefix, `SingularTable`, `NoLowerCase`) set when the database is opened, and `Scanner` / `Valuer` types are not seen: the default naming is assumed, and such a type is an unsupported column unless a `type:` tag names the column type. Not represented, each with a warning naming the struct and field: polymorphic associations (`polymorphic:`; the `<Name>ID` and `<Name>Type` columns stay plain fields), `check:` constraints, column `comment:`, partial (`where:`) and expression indexes, soft delete beyond the nullable `deleted_at` column, integer-backed constant types (a plain integer column), `autoCreateTime` / `autoUpdateTime` on integer fields (Unix time), custom join table and column names, and `serializer:` values other than `json`, `gob` and `unixtime`. GORM ignores a `constraint:` tag on a belongs-to field when the other side describes the same key, and so does the parser (with a warning). Slices and maps without a `type:` or `serializer:` tag, which GORM cannot migrate, are read as arrays and `json` with a warning. Unsigned integers need one more bit in the type mapping, as in GORM's PostgreSQL dialect (`uint32` is `bigInt`).
- Drizzle: only the TypeScript source is read and nothing is executed, so tables built in loops or by functions, column helpers that need run-time values and defaults computed at run time are not seen (each unresolvable table, column, spread, reference or default warns and names the file and table). Not represented, each with a warning: views, sequences, roles and policies, `check()` constraints, partial (`.where()`) indexes (a partial unique index is dropped because a full one would reject rows the source accepts; a partial plain index is read as a full one), expression indexes, index access methods Prisma does not have, `nullsNotDistinct`, `unsigned`, and relations v2 (`defineRelations`; the foreign keys are still read). SQLite `integer({ mode: 'timestamp' })` is read as a date-time column and warns that the database stores Unix time. A SQLite `integer().primaryKey()` is read as written: it is not auto-increment unless `{ autoIncrement: true }` is given, although SQLite assigns row ids anyway. Drizzle has no implicit many-to-many, so the explicit join table is a model and is written as one. Tables referenced but not found in the input get a stub with an auto-increment id. Drizzle can only be read for now; a writer is planned.
- JSON Schema: only JSON is read (no YAML), remote `$ref`s are never fetched and named anchors (`$anchor`, `$dynamicRef`) are not resolved. Relations are inferred from `$ref` properties and the `x-` conventions above, and a few guesses are warned about (a one-to-one pair with no required side, a lone array of models, a missing primary key). See "JSON Schema and OpenAPI" above and the conversion matrix for the full list of what is lost.
- SQL DDL: only the DDL text is read and nothing is run. The dialect is guessed per file, `UNSIGNED`, display widths, time zones and `jsonb` versus `json` are not kept, and names the database generated for constraints are not recorded. Relation names, reverse accessors, enum names and the many-to-many relation name are derived from table and column names, so they are guesses (the conversion matrix lists them). `ALTER TABLE` is replayed for added columns and constraints and a few column options only; renames, dropped columns and type changes are skipped with a warning, so a long migration history is best read from a schema dump. A composite foreign key that points at columns that are themselves single-column foreign keys cannot be expressed, and the Prisma writer reports it. Input is limited to 32 million characters; deeply nested or unterminated constructs are scanned in linear time and never overflow the stack.
- SQLAlchemy and SQLModel: the Python is read statically and nothing is imported, so models built in loops or functions, computed table names, `__table_args__` produced by a `@declared_attr` and column types chosen at run time are not seen. Not represented, each with a warning: check and exclude constraints, partial and expression indexes, single-table inheritance, `column_property` / `composite` / `synonym`, and Python types that need an explicit SQLAlchemy type (`dict`, `list`). Which side of a `relationship()` owns the foreign key is worked out from `foreign_keys`, `remote_side`, `primaryjoin` or the only key between the two tables; an ambiguous pair warns. A many-to-many keeps its two names but not the name or `ondelete` of its association table (see [docs/CONVERSION_MATRIX.md](./CONVERSION_MATRIX.md)).
- Sequelize: the JavaScript or TypeScript is read statically, so nothing is imported or run. Models built in loops or functions, computed model and table names, attribute sets returned by functions, loaders such as `Object.keys(models).forEach(...)`, models added with `sequelize.addModels(path)` and custom inflection (`Sequelize.useInflection`) are not seen (the unresolvable ones warn). Sequelize 6 is the target; Sequelize 7 (`@sequelize/core` and its `@Attribute` decorators) and replaying `sequelize-cli` migrations are not supported yet. Not represented, each with a warning naming the model and field: `DataTypes.VIRTUAL` attributes, getters, setters, hooks, scopes, polymorphic associations (`scope`), `constraints: false` (read as a plain column), index expressions and conditions, and geometry-like PostgreSQL types. A `through` string becomes a many-to-many relation without its own join table name, columns, composite key or timestamps. Writing: the output is Sequelize 6 for the dialects Sequelize has (a MongoDB provider warns and writes PostgreSQL types); Sequelize cannot express generated columns, intervals, ranges and hstore outside PostgreSQL, `ENUM` on SQL Server without losing `NOT NULL`, composite foreign keys or database views (written as models, so `sync()` creates a table), and the `now` default of a created timestamp is left to Sequelize (it sets the value in JavaScript). A string without a length is `TEXT`, and a many-to-many relation has no reverse side unless the schema names one. See "Sequelize" in the field mapping and the conversion matrix.
- Entity Framework Core: the C# is read statically, so nothing is compiled or run and EF Core never builds its model. Reflection, run-time model building, conditionals and loops around configuration code (a loop that assigns `DeleteBehavior` to every foreign key is applied), `ConfigureConventions`, value converters other than `HasConversion<string>()` and the enum-to-string `ValueConverter` class ormbridge writes, and models that live in projects outside the input are not seen (each unreadable piece produces a warning). Types are matched by simple name (namespaces are ignored). Not represented, each with a warning: `OwnsMany`, table-per-type inheritance (table-per-hierarchy is merged into one model), `ToSqlQuery`, filtered and covering indexes, check constraints, comments, seed data, query filters, concurrency tokens and row versions, integer-stored enums (read as enums with the numbers as values) and types without a column type. Names keep their C# case (`Title`), a property initializer is not a database default, and nullable reference types are detected from `#nullable enable` or from reference types written with `?`, because the project file is not read. Migrations are skipped, not replayed. The writer produces EF Core 8 code with the provider's column types; EF Core has no `ON UPDATE` action, no `auto_now` (the context sets an auto-updated column in `SaveChanges`) and no JSON column type on SQLite and SQL Server, and the PostgreSQL-only types (ranges, hstore, `inet`, index methods) need the Npgsql package; each case is a warning.
- SQLAlchemy and SQLModel output: attributes are snake_case (the column name is passed explicitly), a reverse side that the source never named gets the plural of the model name, and the association table of a many-to-many relation has no surrogate `id` (Django's own does, so data needs migrating). Array, HSTORE, range and `INET` columns are PostgreSQL types with a JSON fallback for SQLite only, other databases are not covered, and a `String` without a length cannot be created on MySQL. Views, database schemas, generated-column expressions, index methods and operator classes are not expressed (each warns). SQLModel's `Field` cannot declare an `onupdate` or a named foreign key, so those columns use `sa_column`. The output is not run through Black or Ruff.
- Generated names for Django indexes are shortened to Django's 30-character limit.

Always review the output and run your own migrations/`prisma validate` before applying it to a real database.

## Verified against real tools

The emitters are not only compared with golden files. When the tools are installed, the tests also load the output with the real thing: Django (`manage.py check`, `makemigrations`, `sqlmigrate`, `migrate` and a comparison of the model metadata and the SQLite database with the schema), graphene-django (the generated schema is built, introspected and queried), TypeORM (`tsc` with decorator metadata, TypeORM's metadata validation for every provider and a `synchronize` into in-memory SQLite), Drizzle ORM (`tsc --strict`, `drizzle-kit generate` for PostgreSQL, MySQL and SQLite, `drizzle-kit push` into SQLite, Drizzle's relational configuration and a persistence run on the blog schema), Doctrine, Laravel, GORM and `prisma validate`. These checks are optional: each is skipped with a reason when its tool is missing, and `test/README.md` lists the environment variables (`DJANGO_PYTHON`, `TYPEORM_DIR`, `DRIZZLE_DIR`, `SQLALCHEMY_PYTHON`, `DOCTRINE_DIR`, `LARAVEL_DIR`, `PRISMA_BIN`) and `test/tools/setup-verification-tools.sh`, which installs the Django, TypeORM and Drizzle tools into a scratch directory. The Drizzle parser is checked the other way round: the fixtures are type-checked against `drizzle-orm` and compared with the snapshot `drizzle-kit generate` builds from them. The JSON Schema and OpenAPI fixtures are checked with the real Ajv validator, and the Zod schemas with real Zod 4 (`ZOD_DIR`): they are compiled with `tsc --strict` and parse generated rows (valid ones pass, invalid ones fail). The SQLAlchemy and SQLModel output (`SQLALCHEMY_PYTHON`) is imported with the real libraries, its PostgreSQL DDL rendered, its tables created in SQLite and compared with the schema, and rows are inserted through the ORM (defaults, enums, foreign keys, many-to-many, referential actions). The SQL DDL is executed in SQLite (always), PostgreSQL (`SQL_POSTGRES_URL`) and MySQL or MariaDB (`SQL_MYSQL_URL`), and the tables, columns, keys and indexes the database reports are compared with the schema, and the SQL parser reads the SQLite fixtures back and is compared with what the database reports. The SQLAlchemy parser is checked the other way round: the fixtures are imported, the mappers configured, the tables created in SQLite and read back with the inspector, and one row per table is inserted to see that the defaults work. The Sequelize reader is checked against the real library too: the fixture models are created in in-memory SQLite with `sequelize.sync()` (`SEQUELIZE_DIR`) and the tables, columns, keys, indexes and foreign keys are compared with what the reader found. The Sequelize writer is checked the same way: the models it writes (TypeScript and `sequelize-cli` files, both naming modes) are loaded, `initModels(sequelize)` creates the tables in SQLite, they are compared with the schema, sample rows exercise the defaults, enums, foreign key actions and associations (many-to-many included), the `init` output is type-checked with `tsc --strict`, and the `CREATE TABLE` statements Sequelize builds for PostgreSQL, MySQL and SQL Server are generated without a server. The EF Core reader is checked against the real EF Core 8 too: with the .NET SDK installed (`EFCORE_DIR`, `DOTNET`), the fixtures are compiled, every `DbContext` creates its database in in-memory SQLite with `EnsureCreated()`, and the tables, columns, keys, indexes and foreign keys (with their delete actions) are compared with what the reader found. The EF Core writer is checked the same way: the code it writes (both styles, both naming modes) is compiled with warnings as errors and without implicit usings, the PostgreSQL output against the Npgsql provider, each context creates its SQLite database and it is compared with the schema, and a row is saved into every table through the entity classes to exercise the defaults, enum conversions, generated keys and the `SaveChanges` override.

## Conversion matrix

[docs/CONVERSION_MATRIX.md](./CONVERSION_MATRIX.md) shows, for every pair of readable and writable formats (Django, Prisma, TypeORM, Doctrine, Laravel, GORM, Drizzle, JSON Schema, SQL, SQLAlchemy, Sequelize, EF Core), whether the schema survives a round trip and exactly what is lost when it does not (for example enum labels and column lengths, and Prisma's explicit join model for many-to-many fields). Write-only targets (GORM, Drizzle, JSON Schema and Zod) get a structural check of the written files instead of an IR comparison. It is generated from the test fixtures with `npm run docs:matrix`, and the tests fail if it is out of date.

Django models are read with a static [tree-sitter](https://tree-sitter.github.io/) parser, so **no Python, Django install, or database is needed**.
