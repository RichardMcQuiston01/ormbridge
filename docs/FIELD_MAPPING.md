TypeORM output is a single TypeScript file of entity classes. Relations use `Relation<T>` so entities declared in one file do not trip over circular references, and `--provider` picks the column types (`timestamptz` and `jsonb` for PostgreSQL, `datetime` and `json` for MySQL, `simple-json` for SQLite). Use `--naming normalize` for camelCase properties mapped to snake_case columns with `name:` options. `.ts` is not inferred as a format, so pass `--from typeorm` or `--to typeorm`. Reading uses decorators only (see Limitations). TypeORM entities are parsed statically with tree-sitter (no `reflect-metadata`, TypeScript compiler, or database needed), and the same naming modes apply to the result. The tests compile the emitted entities with `tsc`, build TypeORM's metadata for every provider and synchronize the SQLite output into an in-memory database when TypeORM is installed (`TYPEORM_DIR`, see `test/README.md`).

Doctrine (`--from doctrine`) reads PHP 8 entity classes with the tree-sitter PHP grammar, so no PHP, Composer or database is needed. Pass the entity directory (one class per file is typical; enums and mapped superclasses can live in other files) or individual files; `.php` is not claimed because Laravel uses it too. Doctrine's default underscore naming is assumed for anything the attributes leave out: the table is the snake_cased class name, the column the snake_cased property, a join column `<property>_id`, an embedded column `<property>_<column>`.

Doctrine output (`--to doctrine`) writes a directory, so pass `-o <directory>`. It follows PSR-4: one PHP 8.1+ file per entity (`src/Entity/Post.php`) and one backed enum per enum (`src/Enum/PostStatus.php`), each with `declare(strict_types=1);` and `use Doctrine\ORM\Mapping as ORM;`. `.php` is not inferred, so pass `--to doctrine`.

- **Namespace and paths.** The default namespace is `App\Entity` (enums in `App\Enum`). `--namespace Acme\Blog\Entity` (or `namespace` in the config file, or the `namespace` option of `emitDoctrine` / `convertText`) writes `src/Blog/Entity/Post.php` and puts the enums in `Acme\Blog\Enum`: the first namespace segment maps to `src/`, the rest to folders, and a namespace not ending in `Entity` gets a child `Enum` namespace.
- **Properties.** Typed and nullable (`?int`, `?string`, `DateTimeImmutable`, `bool`), private, with explicit `type:`, `length:`, `precision:` / `scale:`, `nullable:`, `unique:` and the column `name:`. Defaults are PHP property initializers plus `options: ['default' => ...]`; `now` defaults and UUIDs are set in the constructor (no extra packages: UUID keys and defaults use a small private `generateUuid()` helper). Auto-updated timestamps get `#[ORM\PrePersist]` / `#[ORM\PreUpdate]` lifecycle callbacks. Enum columns use `enumType:` with the PHP backed enum, and a default becomes the enum case.
- **Keys.** An auto-increment key is `#[ORM\Id]` with `#[ORM\GeneratedValue(strategy: 'AUTO')]`; composite keys repeat `#[ORM\Id]`, and a relation that is the primary key (multi-table inheritance) carries the `#[ORM\Id]` itself.
- **Relations.** Every relation is written on both sides with matching `inversedBy:` / `mappedBy:`: `ManyToOne` with `JoinColumn(name:, referencedColumnName:, nullable:, onDelete:)` and an inverse `OneToMany`, `OneToOne` with an inverse `OneToOne`, and `ManyToMany` with `JoinTable`, `JoinColumn`, `InverseJoinColumn` and an inverse `ManyToMany`. To-many properties are `Collection` (docblock `Collection<int, Post>`) initialised with `ArrayCollection` in the constructor.
- **Accessors.** Getters and fluent `static` setters (`isFeatured()` for booleans); to-many properties get `getPosts()`, `addPost()` and `removePost()` that keep the owning and inverse sides in sync.
- **Tables and indexes.** `#[ORM\Table(name:)]` plus class-level `#[ORM\Index(columns: [...])]` and `#[ORM\UniqueConstraint(columns: [...])]` on database column names. (`Table(indexes:, uniqueConstraints:)` has no effect in Doctrine ORM 3, so it is not used; ORM 2.19 or newer and PHP 8.1 or newer are required.) Reserved SQL words used as table or column names (`user`, `order`, ...) are written with Doctrine's backtick quoting.
- **Naming.** `preserve` keeps the property names of the source (`published_at`) and always writes the table and column names explicitly; `normalize` writes camelCase properties (`publishedAt`) mapped to snake_case columns. Getter and setter names are always camelCase (`getPublishedAt()`).
- **Lossy or unsupported.** Arrays and HStore become `json` columns; ranges become strings; durations become `dateinterval` (an ISO 8601 string); `GeneratedField` expressions, views, composite foreign keys, `Unsupported(...)` types, full-text indexes, `@@schema` and other Prisma-only constructs are written as plain tables and columns; a relation to a model without a single-column primary key is skipped; each case warns with the model and field. `onUpdate` actions have no Doctrine equivalent. A relation that points at a non-primary-key column (`to_field`) is written, but Doctrine's `orm:validate-schema` rejects it, and the warning says so. Doctrine ORM is relational, so `--provider mongodb` only warns.
- **Reading.** `--from doctrine` reads the same attributes back, the lifecycle callbacks and the constructor and initializer defaults as well, so Doctrine round trips through the shared model. PHP has one empty array literal, so an empty JSON object default (`{}`) comes back as `[]`.

Laravel output (`--to laravel`) writes a directory, so pass `-o <directory>` (the project root of a Laravel 11 or 12 app, for example `-o .`). `.php` is not inferred, so pass `--to laravel` (and `--from laravel` to read a project back, described below). Existing files with the same name are overwritten (use `--check` or `--dry-run` first); the migration file names are fixed (see below), so running the conversion again rewrites the same files rather than adding new ones.

- **Files.** One migration per table in `database/migrations/` (anonymous `return new class extends Migration` with `up()` and `down()` = `Schema::dropIfExists`), one Eloquent model per model in `app/Models/` (namespace `App\Models`) and one backed enum per enum in `app/Enums/` (`App\Enums`). `--namespace Acme\Blog\Models` (or `namespace` in the config file, or the `namespace` option of `emitLaravel` / `convertText`) writes `app/Blog/Models/Post.php` and puts the enums in `Acme\Blog\Enums`; the first namespace segment maps to `app/`.
- **Migration order and names.** Files are named `2024_01_01_000001_create_posts_table.php`, `..._000002_...`, counting up by one, with the date fixed so the output is deterministic. Tables are ordered so a foreign key always points at a table created earlier. A self reference is written inline (`constrained()` on the same table). A real dependency cycle (A needs B, B needs A) creates the tables first and adds the constraints that could not be written in a later `add_foreign_keys_to_<table>_table` migration, whose `down()` drops them. A fresh Laravel app already has a `users` migration, so a `User` model produces a second `create_users_table`: delete one of them.
- **Columns.** `id()` for an auto-increment key (`bigIncrements('code')` when the key is not called `id`; an `int` key becomes a big integer, like Laravel's own `id()`, and foreign keys use `foreignId`), `uuid()->primary()` or `ulid()->primary()` only when the schema says so (with `HasUuids` / `HasUlids` and `foreignUuid` / `foreignUlid` references), `string(n)`, `text`, `integer`, `bigInteger`, `unsignedInteger` and the other sized integers when a Prisma native type (`@db.UnsignedInt`, ...) says so, `double`, `decimal(p, s)`, `boolean`, `dateTime` / `dateTimeTz` / `date` / `time`, `jsonb` on PostgreSQL and `json` elsewhere, `binary`, `ipAddress`, `enum('status', [...])`, `nullable()`, `unique()`, `default(...)` and `useCurrent()` for `now` defaults. A `created_at` + `updated_at` pair becomes `timestamps()` (Eloquent maintains it) and a nullable `deleted_at` becomes `softDeletes()` with `use SoftDeletes`. Indexes and unique constraints are `index([...], 'name')` / `unique([...])`, and composite keys `primary([...])`.
- **Foreign keys.** `foreignId('author_id')->constrained('auth_user')->cascadeOnDelete()` with the matching helper for each action (`restrictOnDelete()`, `nullOnDelete()`, `cascadeOnUpdate()`, ...; `set default` through `onDelete('set default')`). A reference to a non-id column or to a string key is written as `$table->foreign('col')->references('col')->on('table')`.
- **Many-to-many.** A pivot table with both foreign keys and a composite primary key. `normalize` follows Laravel's convention (`post_tag`: singular model names in alphabetical order, `post_id` and `tag_id`) so `belongsToMany(Tag::class)` needs no extra arguments; `preserve` keeps the `<table>_<relation>` name of the other formats and passes the table and key names explicitly. A self relation uses `from_user_id` / `to_user_id`. When the source already models the join table (Prisma's explicit join model), it is an ordinary table and model with `belongsTo` / `hasMany`.
- **Models.** `$table`, `$primaryKey`, `$keyType`, `$incrementing` and `$timestamps` are written only when they differ from what Laravel would guess (`$table` is also written when the plural of the model name is not certain: `Person` is fine, `Axis` is written out). `$fillable` lists every writable column except generated keys and `timestamps()` columns; `$casts` has backed enums, `boolean`, `array` (json columns, arrays, hstore), `datetime`, `date`, `float` and `decimal:N`. Every relation is written on both sides with typed methods and generics docblocks: `belongsTo` (and `hasMany` / `hasOne` on the target), `belongsToMany` on both models, with explicit keys only when they are not Laravel's (`belongsTo(User::class, 'writer_user_id')`). A method that would clash with a column or an Eloquent method gets a `Relation` suffix and a warning.
- **Naming.** `preserve` keeps table and column names exactly (written as `$table` and in the migrations); `normalize` uses plural snake_case tables (`blog_posts`), snake_case columns, `<relation>_id` keys, adds `created_at` / `updated_at` where missing and keeps auto-increment keys as they are. Relationship methods are always camelCase (`editedPosts()`).
- **Lossy or unsupported.** Arrays and HStore become `json` columns, ranges and durations become strings, `GeneratedField` expressions (Python, not SQL), views, composite foreign keys, `Unsupported(...)` types, full-text indexes, index options, `@@schema` and other Prisma-only constructs are written as plain tables and columns; a relation to a model without a single-column primary key is skipped; each case warns with the model and field. Eloquent has no composite primary keys: the migration gets `primary([...])` and the model a warning. An auto-updated column that is not part of `timestamps()` is only refreshed by MySQL (`useCurrentOnUpdate()`). Laravel does not map PostgreSQL-specific types, so `--provider` only chooses `jsonb` versus `json` and the MySQL form of JSON defaults.
- **Not converted.** Policies, factories, seeders, observers, morph relations and anything else outside the schema are not generated, and the models extend `Illuminate\Database\Eloquent\Model` (not `Authenticatable`).

GORM output (`--to gorm`) is write-only and writes a directory, so pass `-o <directory>`: one Go file per model (`models/post.go`, snake_case) and one per enum (`models/post_status.go`), all in the same package, each importing only what it uses and formatted exactly as `gofmt` would (the tests run `gofmt -l`, `go vet` and a SQLite `AutoMigrate` with the real GORM when Go is installed). `.go` is not inferred, so pass `--to gorm`.

- **Package and paths.** The package is `models` and the files go in a directory of that name; `--go-package store` (or `goPackage` in the config file, or the `goPackage` option of `emitGorm` / `convertText`) writes `store/post.go` with `package store`. The name must be a Go identifier that is not a keyword.
- **Fields.** Exported, typed fields with a `gorm:"..."` tag: `string` (`size:n`), `string` with `type:text`, `int32`, `int64`, `float64`, `bool`, `time.Time` (`type:date` for dates), `uuid.UUID` ([google/uuid](https://github.com/google/uuid), `type:uuid` on PostgreSQL, `char(36)` on MySQL), `decimal.Decimal` ([shopspring/decimal](https://github.com/shopspring/decimal) with `type:decimal(p,s)`), `datatypes.JSON` ([gorm.io/datatypes](https://github.com/go-gorm/datatypes)) and `[]byte`. A nullable column is a pointer (`*string`, `*time.Time`, `*uuid.UUID`); `datatypes.JSON` and `[]byte` hold nil themselves. Tags use `column:` (only when GORM would derive another name from the field), `size:`, `primaryKey`, `autoIncrement` (`autoIncrement:false` for a lone integer key without one, because GORM would otherwise add it), `not null`, `unique`, `default:`, `autoCreateTime` / `autoUpdateTime` and the index tags below. A field name is the IR name in Go style (`public_id` becomes `PublicID`).
- **Defaults.** Literal and enum defaults are `default:` tags. A `now` default is `autoCreateTime` and an auto-updated column is `autoUpdateTime`. A UUID default is `default:gen_random_uuid()` on PostgreSQL and a generated `BeforeCreate` hook (`uuid.New()`, or `uuid.NewV7()` for version 7) everywhere else, so the key is known after `Create` on every database.
- **gorm.Model and soft delete.** A model with exactly the `gorm.Model` columns (a big-integer auto-increment `id`, date-time `created_at` and an auto-updated `updated_at`, and a nullable, indexed `deleted_at`) embeds `gorm.Model`, with its other fields after it. A nullable date-time named `deleted_at` on any other model is a `gorm.DeletedAt` field, with a warning, because GORM then hides rows where it is set.
- **Relations.** Every relation is written on both sides. A foreign key is a typed `<Relation><Key>` field (`AuthorID`) plus the association (`Author User` for a required parent that cannot make the type recursive, otherwise `*User`), tagged `foreignKey:AuthorID` (and `references:` for a non-key target) and `constraint:OnDelete:CASCADE` / `OnUpdate:...`, on both the belongs-to and the has-one (`*Profile`) or has-many (`[]Post`) side. Reverse names come from `related_name` or the plural of the model (`Posts`). Many-to-many is `[]Tag` with `many2many:<table>_<relation>`, plus `joinForeignKey` / `joinReferences` when the join columns differ from GORM's (always for a self relation), and `OnDelete:CASCADE` on both sides, since GORM builds the join table from whichever struct it migrates first. Keys that are relations (multi-table inheritance, composite keys of foreign keys) get `primaryKey` on the foreign key field.
- **Tables and indexes.** `func (Post) TableName() string` only when the table is not what GORM derives from the type name (`blog_post`, but not `posts`), using GORM's own naming and pluralization rules (checked against `gorm.io/gorm` in the tests). Indexes are tags on the fields: `index` / `uniqueIndex`, `index:name`, and for composite indexes a shared name with `priority:n` (`idx_<table>_<columns>` when the source has no name).
- **Enums.** A typed string (`type PostStatus string`) with a `const` block in its own file; labels become trailing comments. The column has the enum type and a `default:` for an enum default.
- **Naming.** `preserve` keeps the source's table and column names (explicit `TableName()` / `column:` wherever GORM's convention would differ). `normalize` applies GORM's conventions: plural snake_case tables (`posts`, join tables keep their names), snake_case columns, and `created_at` / `updated_at` where missing; primary keys keep their type (unlike Prisma output, no UUID keys are introduced).
- **Lossy or unsupported.** Integers are signed `int32` / `int64` (the IR has no unsigned types). Arrays become `datatypes.JSONSlice[T]`, HStore `datatypes.JSON`, durations `time.Duration` (nanoseconds in a bigint), ranges strings; generated columns, views, composite foreign keys, `Unsupported(...)` columns (written as `string` with `type:<name>`), full-text indexes and index options, `@@schema` and other Prisma-only constructs are written as plain tables and columns; a relation to a model without a single-column primary key is skipped; each case warns with the model and field. The IR has no check constraints, column comments or polymorphic relations, so no `check:`, `comment:` or `polymorphic:` tags are written. GORM is relational, so `--provider mongodb` only warns. The output needs `gorm.io/gorm`, plus `github.com/google/uuid`, `github.com/shopspring/decimal` and `gorm.io/datatypes` for the types that use them (`go get` them in your module).

Drizzle output (`--to drizzle`) is write-only and writes a directory, so pass `-o <directory>`: `schema.ts` (every enum, table and `relations()` in one file) and `drizzle.config.ts` (`defineConfig` with the matching `dialect`, `schema: './schema.ts'` and `out: './drizzle'`, so `npx drizzle-kit generate` works next to it). One file keeps every table in reach of the others and is what `drizzle-kit` reads without a glob; the tables are ordered so a table follows the tables it references, which keeps circular references compiling without splitting them across modules. `.ts` is not inferred, so pass `--to drizzle`. `drizzle-orm` 0.36 or newer is needed (the table callback returns an array), and `drizzle-kit` for the config.

- **Dialects.** `--provider` picks `drizzle-orm/pg-core` (`postgresql`, `cockroachdb`), `mysql-core` (`mysql`) or `sqlite-core` (`sqlite`); each gets its own table function (`pgTable`, `mysqlTable`, `sqliteTable`) and only the builders it uses are imported. Drizzle has no SQL Server or MongoDB dialect, so those two write PostgreSQL tables and warn.
- **Columns.** Typed builders with the database name as the first argument: `varchar({ length })` (`text` when the source has no length; MySQL needs a length and gets 255), `text`, `integer` / `int`, `bigint({ mode: 'number' })`, `doublePrecision` / `double` / `real`, `numeric` / `decimal({ precision, scale })`, `boolean`, `timestamp({ withTimezone: true })` / `datetime`, `date`, `time`, `uuid` / `char(36)`, `jsonb` / `json`, `inet`, `interval`. On SQLite dates are `integer({ mode: 'timestamp' })`, booleans `integer({ mode: 'boolean' })`, JSON `text({ mode: 'json' })`, decimals `numeric` and UUIDs `text`. `.notNull()` on required columns, `.unique()` (with the constraint name when the source has one), `.array()` for PostgreSQL arrays, and `customType` declarations at the top of the file for the PostgreSQL types Drizzle has no builder for (`bytea`, `hstore`, ranges).
- **Keys and defaults.** An auto-increment key is `serial` / `bigserial` (PostgreSQL), `.autoincrement()` (MySQL) or `.primaryKey({ autoIncrement: true })` (SQLite). A UUID key is `uuid().defaultRandom()`, `.default(sql`(UUID())`)` on MySQL and `$defaultFn(() => crypto.randomUUID())` on SQLite (with a warning: that default only runs for rows inserted through Drizzle). `now` is `.defaultNow()`, `CURRENT_TIMESTAMP` or `(unixepoch())`; literals are `.default(...)` (JSON as an object literal, decimals as strings, date-times as `new Date(...)`); an auto-updated column is `.$onUpdate(() => new Date())`.
- **Enums.** Every enum exports its values (`export const postStatusValues = [...] as const`) and a union type. PostgreSQL adds `pgEnum('name', values)`, MySQL uses `mysqlEnum('column', values)` on the column, SQLite uses `text('column', { enum: values })` (TypeScript only; SQLite gets no check constraint).
- **Relations.** A foreign key is `.references(() => table.id, { onDelete, onUpdate })` (the NO ACTION default is left out; MySQL has no SET DEFAULT and warns), typed after the column it points at (a UUID key gives a `uuid` foreign key). A reference to a table declared later, and a self reference, is annotated `(): AnyPgColumn =>` (`AnyMySqlColumn`, `AnySQLiteColumn`) so TypeScript does not report a circular initializer. `relations()` is written for both sides of every relation: `one()` with `fields` and `references` on the owner, `many()` (`one()` for a one-to-one) on the target, named after `related_name` or the plural of the model; `relationName` is added to both sides when two relations join the same tables or a table points at itself. A many-to-many relation becomes the explicit join table Django creates (a surrogate `id`, two cascading foreign keys, a unique pair) in both naming modes.
- **Indexes and keys.** `index('name').on(table.a, table.b)`, `uniqueIndex(...)` and `primaryKey({ columns: [...] })` (composite keys) in the table callback; unnamed indexes are named `<table>_<columns>_idx` / `_key`, shortened to 63 characters.
- **Names.** TypeScript keys are camelCase in both modes (`createdAt`); tables are camelCase variables of the model name with `export type Post` / `NewPost` row types. `preserve` keeps the source's table, column and enum names as the string arguments; `normalize` applies the fresh-schema style (singular snake_case tables, UUID keys, `created_at` / `updated_at`, snake_case columns).
- **Lossy or unsupported.** Arrays, hstore and ranges outside PostgreSQL become JSON, text or varchar columns and durations integers (microseconds); generated columns (Python), composite foreign keys, views (written as tables), index types, sort orders and operator classes, full-text indexes, `Unsupported(...)` columns and `@@schema` are written as plain tables and columns; client-generated (`cuid()`) and database-expression defaults are dropped; each case warns with the model and field. The IR has no check constraints or column comments, so none are written. The tests compile the output with `tsc --strict`, run `drizzle-kit generate` for all three dialects, `drizzle-kit push` into SQLite and compare the result (and Drizzle's relational configuration) with the schema when Drizzle is installed (`DRIZZLE_DIR`, see `test/README.md`).

Graphene output (`--to graphene`) is write-only and pairs with Django models: it writes one Python file that imports every model from `.models` (generate it with `--to django`, or use your own models) and defines a `DjangoObjectType` per model with an explicit `Meta.fields` list (forward and reverse relations included), a `Query` with a single-item field (`post(id)`) and a list field (`post_list`) per model, `Create`/`Update`/`Delete` mutations built on `graphene.Mutation`, and a final `schema = graphene.Schema(query=Query, mutation=Mutation)`. Inputs map the scalar types to `String`, `Int`, `BigInt`, `Float`, `Decimal`, `Boolean`, `DateTime`, `Date`, `Time`, `UUID` and `JSONString`; a field is required when it is not nullable and has no default, and relations are `ID` inputs (`author_id`, many-to-many `tags_ids`). Enum-backed fields rely on graphene-django's choice conversion for output and are `String` inputs validated by the model. Binary columns and relations to models outside the schema are left out, and models with a composite primary key get only a list query and a create mutation; each case produces a warning naming the model and field. Field names are snake_case like the Django output, `.py` stays owned by Django so pass `--to graphene`, and the naming mode has no effect. Requires graphene-django 3.x at runtime. The tests import the generated schema next to the generated Django models (or, for a Django source, the source models with `django.contrib.auth` installed as the user model) with the real Django and graphene-django when they are installed (`DJANGO_PYTHON`), build it, run the introspection query and create, read, update and delete rows through it.

Django-only constructs: a proxy model (`Meta.proxy = True`) has no table of its own, so it is merged into its concrete model (chains of proxies are followed) and relations that target it are pointed at the concrete model, with a warning. A model with `Meta.swappable = "AUTH_USER_MODEL"` is used as the target of `settings.AUTH_USER_MODEL` and `get_user_model()` instead of an assumed `User`. Custom managers (`objects = MyManager()`, `Manager.from_queryset(...)()`, `QuerySet.as_manager()`) and the classes behind them are ignored without warnings. `django.contrib.postgres` arrays, HStore and range fields, and `GeneratedField` / `db_default` (Django 5.0+), round-trip through `--to django`; the Django emitter writes the `django.contrib.postgres.fields` import and notes the required Django version in a warning.

Prisma → Django applies the reverse mapping. Field names are converted from camelCase to snake_case, with `db_column` set when the column name differs.

## Laravel (`--from laravel`)

Laravel keeps its schema in migrations, not in the models, so `--from laravel` works in two steps, with the tree-sitter PHP grammar (no PHP, Composer or database is needed). First it replays the migration files in order (sorted by file name, which starts with the timestamp) to rebuild the **current** schema: a column added by one migration, renamed by the next and dropped by a third is handled the way the database would. Then it reads the Eloquent models for what the migrations do not say: relation names and their reverse names, casts to backed enums, custom table names and timestamp handling. A table without a model is still converted (its model is named after the singular table name), and `down()` is ignored.

Pass the project root (only `database/migrations` and `app/` are read; `vendor/`, `storage/`, `tests/`, `bootstrap/cache` and `node_modules/` are skipped), or the migrations and model directories separately: `ormbridge convert -i ./database/migrations ./app/Models ./app/Enums --from laravel`. Files are recognised by what they contain, not by where they live: a class whose `up()` calls `Schema::`, a class that extends `Model` (or `Authenticatable`, or another model) and a backed enum, so a flat folder works too. Anonymous (`return new class extends Migration`) and named migration classes are both read. `.php` is not claimed, so pass `--from laravel`. Laravel output (`--to laravel`) is described above.

## GORM (`--from gorm`)

GORM has no schema file: the schema is the Go structs and their `gorm:"..."` tags. `--from gorm` reads them with the tree-sitter Go grammar (no Go toolchain or database is needed, and no Go code is run). Pass the directory that holds the models, or the files; every `.go` file is read, except `*_test.go` and anything below `vendor/`, `testdata/`, `node_modules/` and `.git/`. `.go` is not claimed, so pass `--from gorm`. GORM is read only for now: there is no `--to gorm` yet.

GORM does not mark a model, so a struct is read as one when it embeds `gorm.Model`, has a `gorm:"..."` tag, has a field called `ID`, has a `TableName()` method, or is the target of an association from another model. A struct that is only embedded in others (a shared base) is not a model of its own; unexported fields, `gorm:"-"` fields and `-:migration` fields are not columns.

Names follow GORM's own conventions, so the database names are reproduced exactly: tables are the pluralised snake_case struct name (`BlogPost` becomes `blog_posts`; the plural rules are those of `jinzhu/inflection`, which GORM uses) unless `TableName()` returns another literal or constant, columns are the snake_case field name (`PublicID` becomes `public_id`, with GORM's initialisms such as `ID`, `URL` and `HTTP`) unless `column:` says otherwise, a field called `ID` is the primary key, and a foreign key is `<Field>ID` (`AuthorID` for the field `Author`). The names were checked against GORM v1.31 (`gorm.io/gorm/schema`) for the test fixtures. Struct names are the model names; field names become camelCase (`PublicID` becomes `publicId`).

## Drizzle ORM (`--from drizzle`)

Pass the folder that holds the schema, or the files; every `.ts` file is read (not `*.d.ts`, `*.test.ts`, `*.spec.ts` or anything below `node_modules/`) and only the tables, enums and `relations()` in them are used. `.ts` is TypeORM's extension, so Drizzle is never inferred. ## JSON Schema and OpenAPI (`--from json-schema`)

`--from json-schema` reads JSON Schema (draft 2020-12, 2019-09 and 7) and the `components.schemas` of OpenAPI 3.x (and Swagger 2 `definitions`) documents. It is plain JSON, so nothing is installed or run. Only JSON is read: ormbridge has no YAML parser, so convert a YAML OpenAPI document to JSON first (the error says so). `.json` is too generic to infer and `.schema.json` is not an extension the registry can match (it looks at the last extension only), so pass `--from json-schema`. A directory is read recursively: every `.json` file, except tool configuration (`package.json`, `tsconfig*.json`, ...) and anything below `node_modules/`, `vendor/`, `dist/`, `build/`, `coverage/` and `.git/`.

Every object schema with properties under `$defs`, `definitions` or `components.schemas` is a model (named after its key), and so is a root object schema (named after its `title`, `$id` or file name). Enums, aliases of scalar types and free-form objects are not models.

| `default`                                                                                                                                                       | a literal default (a JSON default is stored as text, an enum default names the member); a date-time default of `now`, `now()` or `CURRENT_TIMESTAMP` is the current time                                                                                                                                      |

| `x-unique`, `x-index`, `x-indexes: [{fields, unique, name}]` (model), `x-table-name` (model)                                                                    | a unique column, indexes, the table name (the model name otherwise)                                                                                                                                                                                                                                           |
| a property named `id` or `<model>Id`, `x-primary-key` (property, several make a composite key, or a model-level array of names)                                 | the primary key; a model without one gets an integer `id` and a warning                                                                                                                                                                                                                                       |
| `$ref` to another model (also inside `allOf: [{...}]`, `anyOf` with null, or with sibling keywords)                                                             | a foreign key (required means not null; `x-on-delete`: `cascade`, `set null`, `restrict`, `no action`, `set default`; `x-related-name`) named `<property>_id`, or the declared `authorId` / `author_id` property next to it                                                                                   |
| an array of `$ref` to a model that references this one                                                                                                          | the reverse side of that foreign key (its `relatedName`); with several candidates `x-related-name` on the foreign key picks one                                                                                                                                                                               |
| arrays of each other on both models                                                                                                                             | a many-to-many field on the model defined first                                                                                                                                                                                                                                                               |
| single references that point at each other                                                                                                                      | a one-to-one relation; the required side holds the key (a warning when that decides nothing)                                                                                                                                                                                                                  |
| `$ref` pointers (`#/$defs/X`, `#/definitions/X`, `#/components/schemas/X`, `#`), `$id`-relative references and relative file references between the input files | followed; a remote reference that is not an input file, a missing target, a named anchor or a reference cycle that never reaches an object keeps the property as a `json` column and warns                                                                                                                    |
| `allOf` composition                                                                                                                                             | the properties of every member are merged into the model (inheritance is flattened, with a warning)                                                                                                                                                                                                           |

A property that is not in `required` is nullable unless it has a `default` or is `readOnly` (the database fills it in). The conventions of ormbridge's own JSON Schema output are read back: a foreign key scalar (`author_id`) next to an optional `$ref` property (`author`) is one relation whose nullability is the scalar's, reverse sides are arrays that are matched with the foreign keys that point at the model (by `x-related-name`, otherwise by position when the counts agree, with a warning), `readOnly` columns are generated, and `bigInt` and `decimal` columns written as patterned strings (`^-?[0-9]+$`, `^-?[0-9]{1,6}(\.[0-9]{1,2})?$`) are read as `bigInt` and `decimal(8, 2)`. Table names, unique constraints, indexes, composite keys, referential actions, related names, enum labels and the exact owner of a many-to-many field are not JSON Schema keywords, so they only survive through the `x-` conventions above, which the writer produces too (see below).

Dropped without a warning: `description` / `title` (the IR has no comments) and validation keywords (`minimum`, `pattern`, ...). Losses reported as a warning naming the model and property: `oneOf` / `anyOf` unions (a property becomes `json`; a `oneOf` of models is not a model), `patternProperties`, maps (`additionalProperties` with a schema), `if` / `then` / `else`, type unions, tuple arrays, nested inline objects (a `json` column; define them under `$defs` to make them models), arrays of models inside other arrays and non-string enums (the plain type is kept). An array of models with no counterpart on the other model gets a nullable foreign key on that model (JSON Schema cannot say who holds the key). The `x-` keywords above are ormbridge's own conventions and are ignored by other tools. [docs/CONVERSION_MATRIX.md](./CONVERSION_MATRIX.md) lists what the reader cannot express.

## SQL DDL (`--from sql`)

`--from sql` reads the SQL that creates a database: a `pg_dump --schema-only`, `mysqldump --no-data` or SQLite `.dump` script, an SSMS-generated script, hand-written DDL, or a folder of plain `.sql` migrations (read in file-name order, so later `ALTER TABLE` statements apply to earlier tables; `*.down.sql`, `*_rollback.sql`, `undo.sql` and similar rollback scripts are skipped). PostgreSQL, MySQL / MariaDB, SQLite and SQL Server are understood, each file in its own dialect, guessed from characteristic syntax (backticks and `ENGINE=`, `AUTOINCREMENT`, `[brackets]` and `GO`, `serial` and `::` casts) and read as PostgreSQL when nothing decides it; `parseSqlDdl` takes a `dialect` option to force one. `tree-sitter-wasms` has no SQL grammar, so a small static tokenizer and statement parser read the text (comments, every quoting style, string escapes, `$$` dollar quoting, `DELIMITER` and `GO` batches, `COPY ... FROM stdin` data and schema-qualified names); nothing is executed and no database is needed. `.sql` is claimed, so a single file infers the format.

## SQLAlchemy and SQLModel (`--from sqlalchemy`)

`--from sqlalchemy` reads SQLAlchemy 2.0 declarative models, the classic `Column(...)` style, `Table(...)` objects and SQLModel classes (the `sqlalchemy` format also covers SQLModel). The Python is read with the same static tree-sitter grammar as Django, so **nothing is imported or run**: no Python, SQLAlchemy or database is needed. `.py` belongs to Django, so pass `--from sqlalchemy`; a directory is walked for `.py` files and skips virtual environments, `site-packages`, `migrations`, `alembic`, `__pycache__`, caches and test or tooling files (`test_*.py`, `*_test.py`, `conftest.py`, `setup.py`).

## Sequelize (`--from sequelize`)

`--from sequelize` reads Sequelize 6 models with the tree-sitter TypeScript grammar, which also reads plain JavaScript (`.js`, `.cjs`, `.mjs`), so **nothing is imported or run**: no Node project, `sequelize` install or database is needed. ## Entity Framework Core (`--from efcore`)

| `[Index(...)]`, `HasIndex(...)`, `HasAlternateKey`, `IsUnique`, `HasDatabaseName`, `IsDescending`                      | indexes and unique constraints (an unnamed unique index over one column becomes a unique field)                                                                                                             |
| `[NotMapped]`, `Ignore()`, computed and get-only properties                                                            | no field                                                                                                                                                                                                    |

## Hibernate / JPA (`--from jpa`)

## TypeScript interfaces (`--to typescript`)

Writes plain TypeScript interfaces and enums for sharing models with a front end (for example an Angular app). It is output only, needs no parser, and `.ts` is not inferred, so pass `--to typescript`.

- One `export interface` per model, with properties in the IR's order, and one string `export enum` per enum using the stored values (a Django choice label becomes a `/** ... */` comment). The IR carries no model or field help text, so no other doc comments are written.
- Types follow what travels as JSON: `string`, `text`, `uuid`, `time`, `bigInt`, `decimal` (to keep precision) and `bytes` (base64) are `string`; `int` and `float` are `number`; `boolean` is `boolean`; `json` is `unknown`. `DateTime` and `Date` are `string` (ISO 8601). Programmatic callers can pass `dates: 'date'` to `emitTypescriptInterfaces` to type them as `Date`; the CLI always writes `string`.
- Nullable fields get `| null`. Fields are never optional, because the interfaces describe the data a server returns, defaults included.
- A foreign key is written as its scalar (`categoryId: number`, typed from the referenced primary key or `to_field`) plus an optional expanded relation (`category?: Category`). Reverse sides are optional (`comments?: Comment[]`, a one-to-one reverse side is `profile?: Profile | null`), as are many-to-many lists on both sides.
- `--naming normalize` writes camelCase property names, `preserve` keeps the existing names. Names that are not valid identifiers are quoted.
- Warnings name the model and field for relations to unknown models, composite-key targets (the foreign key becomes `unknown`), unknown enums or field types, and invalid or clashing type names.

## JSON Schema (`--to json-schema`)

Writes one JSON Schema (draft 2020-12) document describing the rows of every model, for validating API payloads or generating forms and clients. It is output only, needs no parser, and `.json` is not claimed as an extension (the registry matches the last extension and `.json` is far too generic), so pass `--to json-schema` and name the file yourself (for example `-o schema.json`).

- The document has `$schema`, `$id` (`urn:ormbridge:schema`; programmatic callers can pass `id` to `emitJsonSchema`) and `$defs` with one entry per enum and per model. Every model is `type: "object"` with `additionalProperties: false`. Property names match the TypeScript interfaces output, so the two can be used together: `preserve` keeps names, `normalize` writes camelCase.
- **Types.** `string` / `text` are `string` (`maxLength` from the column length), `int` is `integer`, `float` is `number`, `boolean` is `boolean`, `dateTime` / `date` / `time` / `uuid` / `duration` are strings with `format` `date-time` / `date` / `time` / `uuid` / `duration` (a name such as `email` never adds `format: email`), `json` accepts any value, `bytes` is a base64 string (`contentEncoding`). `bigInt` and `decimal` are strings so no precision is lost: `bigInt` has the pattern `^-?[0-9]+$`, and `decimal` has `^-?[0-9]+(\.[0-9]+)?$`, narrowed to the allowed digits when the column has a precision and scale (`decimal(8,2)` is `^-?[0-9]{1,6}(\.[0-9]{1,2})?$`). The IR carries no integer sizes, so `minimum` / `maximum` are written only when a Prisma native type names the width (`@db.SmallInt`, `@db.TinyInt`, `@db.UnsignedInt`, ...). Arrays nest `type: "array"`, HStore is an object of nullable strings and ranges are `{ lower, upper, bounds }` objects.
- **Nullable columns** are `type: ["string", "null"]`. A nullable enum or relation is `anyOf` with `{ "type": "null" }`.
- **Required.** A property is in `required` when its column is not nullable, has no default and is not generated, and a foreign-key scalar is required when its relation is. Columns the database or ORM fills in (auto-increment, UUID, `now`, client-generated and database-expression defaults, auto-updated and generated columns) are `readOnly: true` and not required; a literal or enum default is written as `default` and makes the column optional. Relation and reverse properties are always optional.
- **Relations.** A foreign key keeps its scalar (`author_id`, typed from the referenced key) and gets an optional expanded property that is a `$ref` to the target (`anyOf` with null when nullable). Reverse sides and many-to-many relations are optional arrays of `$ref` (a one-to-one reverse side is nullable), exactly as in the TypeScript output.
- **Enums** are `{ "type": "string", "enum": [stored values] }`. The IR has no column comments, so `description` carries only enum labels (`draft: Draft`) and generated-column expressions.
- **OpenAPI.** An OpenAPI 3.1 document uses JSON Schema 2020-12, so the entries can be copied into `components.schemas`. References point at `#/$defs/<Name>` by default; pass `refPrefix: '#/components/schemas/'` to `emitJsonSchema` and copy the `$defs` entries over (or rewrite the prefix with a text replace). Generating an OpenAPI document itself (paths, `--to openapi`) is not part of this format.
- Warnings name the model and field for relations to unknown models, composite-key targets (the foreign key accepts any value), unknown enums or field types, duplicate enum values, and definition names that cannot be used in a `$ref` (they are renamed). Database constraints have no JSON Schema keyword, so they are written as ormbridge's own `x-` keywords, which the JSON Schema reader reads back: `x-table-name` (when the table is not named after the definition), `x-primary-key` (a key that is not called `id`, or a composite key as an array of property names), `x-unique` on a column, `x-indexes` (`{ fields, unique?, name? }` entries), and on a relation property `x-on-delete` (only when it differs from what the reader assumes: `restrict` for a required relation, `set-null` for an optional one) and `x-related-name` (the name of the reverse property). Other tools ignore these keywords, but **Ajv in strict mode rejects unknown keywords**: register them with `ajv.addVocabulary(JSON_SCHEMA_CONVENTION_KEYWORDS)` (exported by the package), or pass `--no-conventions` (config key `conventions: false`; `conventions: false` in the API) for a document without them. Index methods, operator classes, sort orders, full-text kinds, `onUpdate` actions and constraint names have no convention and are not written.
- The tests check every canonical fixture's output structurally and, when Ajv is installed (`AJV_DIR`, see `test/README.md`), load it with the real draft 2020-12 validator and validate IR-generated sample rows.

## Zod schemas (`--to zod`)

Writes [Zod](https://zod.dev) 4 schemas and their inferred types, for validating the same data the TypeScript interfaces describe. It is output only, writes one `schemas.ts`-style file (`import { z } from 'zod'` first), and `.ts` is not inferred, so pass `--to zod`. Property names, enum names and the handling of relations follow the TypeScript interfaces emitter, so the two outputs can be used together.

- **Per model**: `<Model>Schema` (`z.object({...})`) and `export type <Model> = z.infer<typeof <Model>Schema>`; `<Model>CreateSchema` / `<Model>Create`; `<Model>UpdateSchema` / `<Model>Update`.
- **Create schema**: leaves out what the database generates (auto-increment keys, generated columns, auto-updated timestamps such as Django `auto_now` and Prisma `@updatedAt`), and makes columns with a default (or a database default) and nullable columns `.optional()`. The **update schema** is `<Model>CreateSchema.partial()`. A view gets neither.
- **Types**: `string` and `text` are `z.string()` with `.max(n)` from the length; `uuid` is `z.uuid()` (Zod's RFC 9562 check; use `z.guid()` if your data holds other UUID-shaped values); `int` is `z.number().int()`; `float` is `z.number()`; `boolean`; `json` is `z.unknown()`; `bytes` is `z.base64()`; IP addresses are `z.union([z.ipv4(), z.ipv6()])`; times and durations are `z.string()`. `bigInt` is a string of digits (`z.string().regex(/^-?\d+$/)`, like the TypeScript interfaces, because JSON cannot carry a bigint) and `decimal` is a string matching a number pattern sized from `max_digits` and `decimal_places`, to keep precision. Arrays wrap the element in `z.array(...)`, nullable columns get `.nullable()`, hstore is `z.record(z.string(), z.string().nullable())` and a range is an object with nullable `lower` and `upper` plus `bounds`. No `z.email()` or `z.url()` is ever inferred from a name.
- **Dates** are `z.coerce.date()`: they accept a `Date` or any value `new Date(value)` accepts (ISO text from JSON) and produce a `Date`. Coercion also turns `null` (and numbers) into a date, so a null in a required date column is not rejected; use a nullable column, or pass `dates: 'string'` to `emitZod` for strict ISO text (`z.iso.datetime({ offset: true })` / `z.iso.date()`, which matches the TypeScript interfaces' default). Pass `bigints: 'bigint'` for `z.coerce.bigint()`. The CLI always writes the defaults.
- **Enums** are a const object with the stored values (`export const Role = { ADMIN: 'admin' } as const;`, so `Role.ADMIN` works like the interface emitter's enum), `export const RoleSchema = z.enum(Role)` and `export type Role = z.infer<typeof RoleSchema>`. Labels become comments.
- **Relations** are not part of `<Model>Schema`: the foreign-key scalar stays a field (`categoryId`, typed from the referenced key) and relation fields are left out, so a row validates exactly what a table row holds. A model that takes part in a relation also gets `<Model>WithRelationsSchema` (and a hand-written `<Model>WithRelations` type, because mutually recursive schemas cannot be inferred), which extends the row with optional, lazily resolved related rows (`z.lazy`), reverse sides and many-to-many lists included.
- `--naming normalize` writes camelCase property names, `preserve` keeps the existing names. Warnings name the model and field for relations to unknown models, composite-key targets (the foreign key becomes `z.unknown()`), unknown enums or field types, and invalid or clashing type names.
- **Zod 3**: the output uses Zod 4 APIs (`z.uuid()`, `z.base64()`, `z.ipv4()`, `z.enum(constObject)`, `z.iso.*`). Zod 3.25 and later ship Zod 4 under `zod/v4`, so change the import to `import { z } from 'zod/v4'`; older Zod 3 releases are not supported.

## SQL DDL (`--to sql`)

Writes one `.sql` script of dialect-specific DDL, so the schema can be created in a database directly (or reviewed before a migration is written). It is output only, `.sql` is inferred from the output path, and `--provider` picks the dialect: `postgresql` (also used for `cockroachdb`), `mysql`, `sqlite` or `sqlserver` (`mongodb` has no SQL and falls back to PostgreSQL with a warning). The script holds, in order, the extensions and enum types the dialect needs, one `CREATE TABLE` per model with the tables a table references created first, and the `CREATE [UNIQUE] INDEX` statements of each table. A foreign key that closes a reference cycle is added afterwards with `ALTER TABLE ... ADD CONSTRAINT` (SQLite cannot add a constraint later, but accepts a reference to a table created further down, so its keys stay inline).

- **Naming** follows the other emitters: `preserve` keeps the table and column names of the source, `normalize` writes singular snake_case tables with UUID keys, snake_case columns and `created_at` / `updated_at`. Identifiers are bare when they are lower-case words that are not reserved in any of the four dialects, otherwise quoted for the dialect (`"x"`, `` `x` `` or `[x]`, with the quote character doubled); quotes in string literals are doubled, and MySQL also doubles backslashes. Names longer than the dialect allows give a warning, and generated constraint and index names are shortened with a hash.
- **Types**: `string` is `VARCHAR(n)` (`TEXT` without a length on PostgreSQL and SQLite, `VARCHAR(255)` on MySQL, `NVARCHAR(n)` on SQL Server), `text` is `TEXT` / `LONGTEXT` / `NVARCHAR(MAX)`, `decimal` keeps its precision and scale, `uuid` is `UUID` / `CHAR(36)` / `UNIQUEIDENTIFIER`, `dateTime` is `TIMESTAMPTZ` / `DATETIME(6)` / `DATETIME` / `DATETIME2`, `json` is `JSONB` / `JSON` / `TEXT` with a `json_valid` check / `NVARCHAR(MAX)` with an `ISJSON` check, and booleans are `BOOLEAN` (`BIT` on SQL Server). A Prisma native type (`@db.VarChar`, `@db.Uuid`, `@db.UnsignedInt`, ...) is kept when the dialect has a type of that name and ignored otherwise. Arrays, ranges, hstore and `interval` are PostgreSQL types; the other dialects get JSON or text (an integer of microseconds for durations) with a warning.
- **Defaults**: literals are quoted and typed for the dialect (booleans are `TRUE` / `FALSE` or `1` / `0`), `now` is `now()`, `CURRENT_TIMESTAMP`, `CURRENT_TIMESTAMP(n)` or `SYSUTCDATETIME()`, and a UUID default is `gen_random_uuid()`, `(UUID())`, `NEWID()` or an expression over `randomblob` on SQLite. Well-known database expressions (`gen_random_uuid()`, `now()`, `uuid_generate_v4()`, `CURRENT_TIMESTAMP`) are translated to the dialect; any other expression is written as it is with a warning. Defaults generated by the ORM client (`cuid()`, `ulid()`) are dropped with a warning. A column the ORM refreshes on update gets `ON UPDATE CURRENT_TIMESTAMP` on MySQL; the other dialects need a trigger, which is not generated, so one warning lists those columns.
- **Keys**: auto-increment is `GENERATED BY DEFAULT AS IDENTITY`, `AUTO_INCREMENT`, `INTEGER PRIMARY KEY AUTOINCREMENT` or `IDENTITY(1,1)`; primary keys (also composite) are named `CONSTRAINT <table>_pkey`; unique fields are `UNIQUE` constraints and composite unique keys are `CREATE UNIQUE INDEX`; on SQL Server a unique key over a nullable column is a filtered unique index (`WHERE col IS NOT NULL`), so it allows many NULLs like the other databases. Foreign keys are named `<table>_<column>_fkey` and carry `ON DELETE` / `ON UPDATE` (`NO ACTION`, the default, is left out); composite foreign keys, `toField` targets and keys that are themselves relations (multi-table inheritance) are supported. MySQL has no `SET DEFAULT`, and SQL Server rejects cascading actions that form a cycle or a second cascade path: both are written as `NO ACTION` with a warning.
- **Indexes** carry their sort order, the PostgreSQL access method and operator class, MySQL prefix lengths and `USING`, SQL Server `CLUSTERED` / `NONCLUSTERED`, and full-text indexes (`FULLTEXT` on MySQL, a `gin` index over `to_tsvector` on PostgreSQL, an ordinary index with a warning elsewhere). An index or unique key on a column the dialect cannot index (a `JSON` column on MySQL, `NVARCHAR(MAX)` on SQL Server) is left out with a warning, and one on a MySQL `TEXT` or `BLOB` column covers its first 255 characters.
- **Enums**: PostgreSQL gets `CREATE TYPE ... AS ENUM` (renamed with an `_enum` suffix when a table has the same name), MySQL an inline `ENUM(...)`, SQLite and SQL Server a text column with a `CHECK (column IN (...))` constraint. Member names and labels are not kept.
- **Many-to-many** fields become the join tables the other formats create. **Views** have no query in the IR, so they are a commented placeholder (`-- CREATE VIEW ... AS SELECT ... ;`) and a warning.
- Warnings name the model and field for what the dialect cannot express: relations to unknown models, views or composite keys, unknown enums or field types, generated-column expressions (not SQL), database schemas (`@@schema`, ignored), unreferenceable targets, `SET NULL` on a required relation and every default or index option that was dropped.
- The tests execute the output: SQLite always (Node's built-in `node:sqlite`, or `better-sqlite3`), PostgreSQL when `SQL_POSTGRES_URL` is set and MySQL or MariaDB when `SQL_MYSQL_URL` is set (see `test/README.md`). After running the script they read the tables, columns, keys and indexes back and compare them with the schema, and insert rows to check defaults, identity, enums and referential actions. SQL Server has no server in the tests; its output is covered by the golden files and unit tests only.

## SQLAlchemy and SQLModel (`--to sqlalchemy`)

Writes [SQLAlchemy](https://www.sqlalchemy.org) 2.0 declarative models, or with `--style sqlmodel` [SQLModel](https://sqlmodel.tiangolo.com) classes. It is output only and writes **one `models.py`** (like Django, so `-o` is a file and the output can be printed to stdout); `.py` is inferred as Django, so pass `--to sqlalchemy`. The output needs Python 3.9 or newer and SQLAlchemy 2.0 or newer (SQLModel 0.0.21 or newer for `--style sqlmodel`). `--provider` is ignored: the models do not depend on the database.

- **SQLAlchemy style** (default): `class Base(DeclarativeBase)`, one class per model with `__tablename__`, typed `Mapped[...]` attributes built with `mapped_column`, and `relationship(back_populates=...)` on **both** sides of every relation (a forward `Mapped["User"]` / `Mapped[Optional["User"]]` and a reverse `Mapped[list["Post"]]`; the reverse side of a one-to-one is `Mapped[Optional["Profile"]]`). Python `enum.Enum` classes are bound with `Enum(Cls, name=..., values_callable=...)`, so the database stores the enum values, not the member names. Only the imports the module uses are written, forward references are strings, and classes follow the classes their foreign keys point at.
- **SQLModel style**: `class Post(SQLModel, table=True)` with `Field(...)` and `Relationship(back_populates=...)`. Types SQLModel infers from the annotation (`str`, `int`, `bool`, `date`, `uuid.UUID`, ...) are left to it, `max_length`, `max_digits` and `decimal_places` carry lengths and precision, and `sa_type`, `sa_column_kwargs`, `sa_relationship_kwargs` and (for a foreign key with `onupdate`, `NO ACTION` or a constraint name, which `Field` cannot say) `sa_column` appear only where needed. A column the database fills in is `Optional[...] = Field(default=None, nullable=False, ...)`.
- **Naming**: attributes are snake_case in both modes, with the database name as the first argument of `mapped_column` (or `sa_column_kwargs={"name": ...}`) when it differs. `preserve` keeps table, column, index and enum type names; `normalize` writes singular snake_case tables, UUID keys, snake_case columns and `created_at` / `updated_at`. An attribute that would shadow Python or SQLAlchemy (`class`, `metadata`, `text`, `datetime`, an enum or model name, and for SQLModel `json`, `copy`, `schema`, ...) gets a trailing underscore, a class that collides with an import gets a `Model` suffix, and enum members that are not identifiers are repaired; each repair is a warning. An unnamed reverse relation is named after the plural of the model (`posts`), a one-to-one after the model, and two relations from one model to the same target get `posts_author` / `posts_editor`.
- **Types**: `String(n)`, `Text`, `Integer`, `BigInteger`, `Float`, `Numeric(p, s)`, `Boolean`, `DateTime(timezone=True)`, `Date`, `Time`, `Interval`, `Uuid`, `JSON` (`JSON(none_as_null=True)` for a nullable column) and `LargeBinary`. Arrays (`ARRAY`, `dimensions=` for nested ones), `HSTORE`, range types and `INET` are PostgreSQL types; each is written with a `.with_variant(JSON(), "sqlite")` fallback (a `String(45)` for `INET`) so `create_all` also works in a SQLite test database, with a warning. A big auto-increment key is `BigInteger().with_variant(Integer, "sqlite")`.
- **Defaults**: literal, enum, boolean and `now` defaults are `server_default` (`func.now()`, `true()`, `text(...)`), UUID defaults are `default=uuid.uuid4`, an auto-updated column is `default=func.now(), onupdate=func.now()`, and a Prisma `dbgenerated(...)` expression is `server_default=text(...)`. Client-generated defaults (`cuid()`, `ulid()`) and Prisma default functions are dropped with a warning; a UUID version 7 default is written as `uuid4` with a warning.
- **Keys**: composite and named primary keys are a `PrimaryKeyConstraint`, composite foreign keys a `ForeignKeyConstraint` (with their relationship), unique and index entries `UniqueConstraint` / `Index` in `__table_args__` (generated names are `ix_<table>_<columns>` / `uq_...`; names the source gives are kept). `ForeignKey(..., ondelete=..., onupdate=...)` carries the referential actions, and the reverse side of a cascading or nulling key sets `passive_deletes=True`. A foreign key takes its column type from the key it references (`toField` targets and keys that are themselves relations are followed). `SET NULL` on a required relation is written as `RESTRICT` with a warning. Two foreign keys between the same tables, and self references, get `foreign_keys=` / `remote_side=`.
- **Many-to-many** relations are a `Table(...)` with the two foreign keys as a composite primary key (no surrogate `id`, unlike the table Django creates), named `<owner table>_<relation>` and used as `secondary=` on both relationships; a self reference adds `primaryjoin` / `secondaryjoin`. The table is defined before the classes.
- **Views** are a commented placeholder (SQLAlchemy has no declarative view; reflect it with `Table(..., autoload_with=engine)`) and a warning. A table without a primary key is mapped on its required columns with `__mapper_args__` (SQLModel needs a key, so its first column is marked) and a warning. Database schemas (`@@schema`), generated-column expressions (not SQL), index methods, operator classes, sort order and full-text kinds are dropped with a warning, and a relation to a view or to a model that is not in the input stays a plain column.
- The tests load the output with real SQLAlchemy 2 and SQLModel (`SQLALCHEMY_PYTHON`, see `test/README.md`): the models are imported, the mappers configured, the PostgreSQL DDL rendered, the tables created in SQLite, and the columns, keys, indexes and relationships compared with the schema; rows are inserted (defaults, enums, foreign keys, many-to-many through the relationships) and the referential actions exercised.

## Sequelize (`--to sequelize`)

Writes [Sequelize](https://sequelize.org) 6 models, one file per model plus an `index` file, so `-o` is a directory (`.ts` and `.js` are not inferred, so pass `--to sequelize`). The generated code needs `sequelize` 6 (and TypeScript, or `tsx`, for the default style). The details, with examples, are in the [Sequelize guide](formats/sequelize.md#writing).

- **Styles** (`--style`): `init` (default) writes TypeScript: `class Post extends Model<InferAttributes<Post>, InferCreationAttributes<Post>>` with `declare` fields (`CreationOptional`, `| null`, string-literal unions for enums, `NonAttribute<...>` associations), a static `initModel(sequelize)` that calls `Post.init({ ... }, { sequelize, modelName, tableName, ... })`, and an `index.ts` whose `initModels(sequelize)` initializes every model and then runs the associations. `define` writes the `sequelize-cli` CommonJS layout: `module.exports = (sequelize, DataTypes) => { const Post = sequelize.define(...); Post.associate = (models) => {...}; return Post; }` per model and an `index.js` with `initModels(sequelize)`.
- **Naming**: `preserve` writes every `tableName` and `field` explicitly and keeps the attribute names of the source (so the models match an existing database); `normalize` writes singular snake_case tables, UUID keys, `created_at` / `updated_at` and camelCase attributes over snake_case columns (`underscored: true`). Model and class names are PascalCase in both.
- **Types**: `STRING(n)`, `TEXT`, `INTEGER`, `BIGINT`, `DOUBLE`, `DECIMAL(p, s)`, `BOOLEAN`, `DATE`, `DATEONLY`, `TIME`, `UUID`, `BLOB`, `ENUM(...)`. A string without a length is `TEXT` (`STRING` when it is a key or indexed). `--provider postgresql` adds `JSONB`, `ARRAY(type)`, `INET`, `HSTORE`, `RANGE(type)` and the `GEOMETRY`, `GEOGRAPHY`, `CIDR`, `MACADDR`, `TSVECTOR` and `CITEXT` unsupported types; on MySQL and SQLite a JSON column is `JSON` and arrays and hstore fall back to `JSON` (a range to `TEXT`, an `INET` to `STRING(45)`) with a warning, on SQL Server JSON and arrays are `TEXT` and enums `STRING` with a warning. Durations are `BIGINT` microseconds and generated columns are regular columns, with a warning.
- **Defaults**: literals, `DataTypes.NOW`, `DataTypes.UUIDV4` / `UUIDV1`, enum values, JSON object literals and `Sequelize.literal('...')` for database expressions (parenthesized for SQLite and MySQL). Client-generated defaults (`cuid()`, `ulid()`), UUID versions other than 1 and 4 and array defaults other than `[]` are dropped or approximated with a warning.
- **Keys**: `primaryKey` on each member of a composite key, `autoIncrement` on a single integer key, `unique: true` (or the constraint name), and `indexes: [{ fields, unique, name, using, type }]` with the column names, sort order, prefix length and operator class. A model without a key gets `removeAttribute('id')`.
- **Timestamps**: a required `created_at` / `createdAt` date-time and a required auto-updated date-time become `timestamps: true` with `createdAt` / `updatedAt` names (the `init` style also lists the columns, as `{ type: DataTypes.DATE, allowNull: false }`, for the TypeScript types); without them `timestamps: false`. The `now` default of the created column is not written, because Sequelize sets it in JavaScript. `paranoid` is never written.
- **Associations**: the foreign key column is declared on the model (type from the referenced key) and the relation is `belongsTo` with `as`, `foreignKey` and `onDelete`, plus `hasMany` / `hasOne` (a one-to-one column is `unique: true`) when the relation has a related name; `onUpdate` only when it is not `CASCADE`, `targetKey` / `sourceKey` for a column other than the primary key. A many-to-many relation is `belongsToMany` with `through: '<table>_<relation>'`, `foreignKey` / `otherKey` (`<model>_id`, `from_` / `to_` for a self reference) and `timestamps: false`; an explicit join model is an ordinary model. Composite foreign keys, relations to missing models and many-to-many relations over composite keys are not written (warning).
- **Not written**, each with a warning naming the model and field: generated columns, views (written as models), `@@ignore`, enum database schemas, clustered indexes, index methods and full-text indexes outside PostgreSQL and MySQL.

## Entity Framework Core (`--to efcore`)

Writes [Entity Framework Core](https://learn.microsoft.com/ef/core/) 8 models in C# with `#nullable enable`: one class per model in `Models/`, one `enum` per enum and an `AppDbContext` with a `DbSet<T>` per entity, so `-o` is a directory (`.cs` is not inferred, so pass `--to efcore`). The generated code needs `Microsoft.EntityFrameworkCore` 8 and a provider. The details, with examples, are in the [Entity Framework Core guide](formats/efcore.md#writing).

- **Styles** (`--style`): `annotations` (default) puts data annotations on the classes (`[Table]`, `[Column]`, `[Key]`, `[MaxLength]`, `[Precision]`, `[Index]`, `[ForeignKey]`, `[InverseProperty]`, `[DatabaseGenerated]`) and uses the fluent API in `OnModelCreating` only for what annotations cannot say (defaults, enum conversions, delete behaviors, join tables). `fluent` writes plain classes and one `IEntityTypeConfiguration<T>` per entity in `Configurations/`, applied from `OnModelCreating`.
- **Naming**: `preserve` keeps the table and column names of the source (`[Table]` / `[Column]` whenever they differ from EF Core's), `normalize` writes singular snake_case tables and columns, UUID keys and `created_at` / `updated_at`. Class and property names are PascalCase in both; the `DbSet` is the plural of the class.
- **Types**: `string` (`[MaxLength(n)]`), `int`, `long`, `double`, `decimal` (`[Precision(p, s)]`), `bool`, `DateTime`, `DateOnly`, `TimeOnly`, `TimeSpan`, `Guid`, `byte[]`; nullable columns are `int?` / `string?`. JSON is a `string` with the column type `jsonb` (PostgreSQL) or `json` (MySQL), plain text with a warning on SQLite and SQL Server. PostgreSQL also gets arrays, `IPAddress`, `Dictionary<string, string>` (hstore) and `NpgsqlRange<T>`; other providers fall back to a string, with a warning.
- **Defaults**: typed `HasDefaultValue(...)` for literals and enum members, `HasDefaultValueSql(...)` for `now` (`CURRENT_TIMESTAMP`, `GETUTCDATE()` on SQL Server), database UUID functions and expressions; a UUID default on SQLite is `HasValueGenerator<GuidValueGenerator>()` with a warning. Client-generated defaults (`cuid()`, `ulid()`) are dropped with a warning.
- **Enums**: a C# `enum`; `HasConversion<string>()` when the members are named like the stored values, otherwise a `ValueConverter<TEnum, string>` class in the enum file; integer values are plain members with numbers.
- **Keys and indexes**: `[Key]` for a key that is not `Id` / `<Class>Id`, `[PrimaryKey(...)]` for a composite key, `[DatabaseGenerated]` where EF Core's conventions differ, `[Index(...)]` with `IsUnique`, `Name` and `IsDescending`, `HasAlternateKey` for a column another table references, `HasMethod` for index methods on PostgreSQL. A model without a key is `[Keyless]` with a warning.
- **Relations**: a foreign key property plus a navigation (and, with a related name, the collection or the single navigation on the other side); `OnDelete(DeleteBehavior.X)` where it differs from EF Core's default, `HasPrincipalKey` for a column other than the key, composite foreign keys with `HasForeignKey(e => new { ... })`. A many-to-many relation is two skip navigations with `UsingEntity<Dictionary<string, object>>` naming the join table the other formats create.
- **Timestamps**: an auto-updated date-time is `ValueGeneratedOnAddOrUpdate()` and `AppDbContext` sets it in `SaveChanges` / `SaveChangesAsync`, because EF Core has no `auto_now`.
- **Not written**, each with a warning naming the model and field: `ON UPDATE` actions and `SET DEFAULT`, client-generated defaults, array defaults, PostgreSQL-only types on other providers, generated columns whose expression is Python, `@@ignore`, enum database schemas, clustered indexes, prefix lengths and operator classes.

## Hibernate / JPA (`--to jpa`)

Writes Hibernate / JPA entities in Java: one `@Entity` class per model, one `enum` per enum, an `AttributeConverter` for an enum whose stored values differ from its names and an `@IdClass` class per composite key, so `-o` is a directory (`.java` is not inferred; pass `--to jpa`). The classes go in the folder of the Java package, `--namespace` (default `app.models`), and use private fields with getters and setters. See the [Hibernate / JPA guide](formats/jpa.md#writing) for the full table.

- **Styles** (`--style`): `jakarta` (default; `jakarta.persistence`, Hibernate 6, Spring Boot 3) or `javax` (`javax.persistence`, Hibernate 5, Spring Boot 2). Where Hibernate 5 has no mapping (JSON, arrays, generated columns, `@OnDelete` other than CASCADE, non-key UUID generators) the closest type is written and a warning says so.
- **Naming**: `preserve` keeps the database names, `normalize` writes singular snake_case tables and columns, UUID keys and `created_at` / `updated_at`. Every table, column and join column is named explicitly, so the schema does not depend on a naming strategy.
- **Types**: `String` (`@Column(length)`), `int` / `Integer`, `long` / `Long`, `double` / `Double`, `boolean` / `Boolean`, `BigDecimal` (`precision`, `scale`), `LocalDateTime` (`OffsetDateTime` for `timestamptz`), `LocalDate`, `LocalTime`, `Duration`, `UUID`, `byte[]`. Required columns without a database-only default use the primitive. `text` is `columnDefinition = "text"` on PostgreSQL and `@Lob` elsewhere; JSON is `@JdbcTypeCode(SqlTypes.JSON)`; arrays are Java arrays on PostgreSQL.
- **Defaults**: `@ColumnDefault` plus a field initializer for literals and `now`; a database expression adds `@DynamicInsert`. `@CreationTimestamp` on `created_at`, `@UpdateTimestamp` on auto-updated columns, `@UuidGenerator` for a UUID default.
- **Enums**: `@Enumerated(EnumType.STRING)` when the constants are named like the stored values, `ORDINAL` for positions, otherwise constants that carry the value and a converter (`@Convert(converter = ...)`).
- **Keys and indexes**: `@Id` with `@GeneratedValue` (IDENTITY, UUID), `@IdClass` for a composite key (a relation in the key is an `@Id @ManyToOne`), `@Table(uniqueConstraints, indexes)` with `DESC` in `columnList`.
- **Relations**: `@ManyToOne` / `@OneToOne` with `@JoinColumn(name, referencedColumnName, nullable, foreignKey)` and `@OnDelete`, the reverse side with `mappedBy` (a `List` or a `Set`), `@ManyToMany` with `@JoinTable`, composite foreign keys with `@JoinColumns` (read-only next to the scalar columns).
- **Not written**, each with a warning naming the model and field: `ON UPDATE` actions, index types, clustering and operator classes, full-text indexes, hstore and range columns, client-generated defaults, auto-increment outside the key, views (written `@Immutable`), and a model without a primary key (one column becomes the `@Id`). `@Version` is never written.
