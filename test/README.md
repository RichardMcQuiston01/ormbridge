# Test harness

One canonical schema (the "blog" models) is expressed in every readable format. The shared tests in `conversion.test.ts` convert it between every registered format pair and compare the result with stored golden files.

## Adding a format

1. Express the canonical schema in your format and add the file(s) under `test/fixtures/`.
2. Add one entry to `CANONICAL_FIXTURES` in `test/fixtures/canonical.ts`.
3. Run `UPDATE_GOLDEN=1 npm test` to create the golden files for your format, then review the new files in `test/golden/` before committing.

A test fails if a readable format has no canonical fixture.

## Helpers (`harness.ts`)

- `loadCanonicalSources(format)` and `convertCanonical(from, to, overrides)` read and convert a fixture.
- `expectMatchesGolden(name, text)` compares text with `test/golden/<name>`. Set `UPDATE_GOLDEN=1` to write it instead.
- `roundTrip(from, via)` converts `from -> via -> from -> via`. `describeDrift(before, after)` lists the lines that changed.

## Multi-file formats

An emitter that returns a file map (such as `doctrine`) is compared file by file: its golden is the directory `test/golden/<pair>.<naming>/` with one golden file per generated file at the same relative path, instead of `<pair>.<naming>.txt`. `expectConversionMatchesGolden(pair, naming, result)` picks the right form; `expectFilesMatchGolden(name, files)` is the directory form. A file that is generated without a golden, or a golden that is no longer generated, fails the test and is named; `UPDATE_GOLDEN=1` rewrites the whole directory, so goldens of removed files disappear. `conversion.test.ts` also fails when `test/golden/` contains an entry that no format pair produces.

Round trips (`roundTrip`) feed every emitted file back into the parser (`resultToSources`) and `describeResultDrift` lists drift per file (`@@ path`, `+ file path`, `- file path`). The matrix helpers do the same (`emitWith` keeps the file map next to the joined text, `parseEmitted` reads all of the files). `harness.test.ts` covers this with a test-only readable multi-file format, so a multi-file format that also gets a parser (Doctrine, Laravel) joins the round trips and the matrix without further changes.

The SQL DDL emitter (`sql-ddl-emitter.test.ts`) writes one text. Its default (PostgreSQL) conversions are the usual `test/golden/<format>-to-sql.<naming>.txt` files. The MySQL, SQLite and SQL Server output of every canonical schema (`test/golden-extras/sql-<provider>/<format>-to-sql/`), all four dialects of the extras fixtures (`sql-extras/`) and of the IR fixtures (`sql-fixtures/`) are directories with one `preserve.sql`, `normalize.sql` and a `.warnings.txt` for each, compared with `expectFilesMatchGolden`.

The Drizzle emitter (`drizzle-emitter.test.ts`) writes two files, so its default (PostgreSQL) conversions are the directories `test/golden/<format>-to-drizzle.<naming>/` like any multi-file format. The MySQL and SQLite output of every canonical schema and all three dialects of the IR fixtures live in `test/golden-extras/drizzle-mysql/`, `drizzle-sqlite/` and `drizzle-fixtures/` (each with a `warnings.txt`), compared with `expectFilesMatchGolden` against that root. `.prettierignore` lists the generated `.ts` goldens: they are compared byte for byte and are not Prettier-formatted.

The SQLAlchemy emitter (`sqlalchemy-emitter.test.ts`) writes one text, so its default (`sqlalchemy` style) conversions are the usual `test/golden/<format>-to-sqlalchemy.<naming>.txt` files. The SQLModel output of every canonical schema (`test/golden-extras/sqlmodel/<format>-to-sqlalchemy/` with `preserve.py`, `normalize.py` and a `.warnings.txt` for each) and both styles and naming modes of the extras and IR fixtures (`test/golden-extras/sqlalchemy-fixtures/<label>/`) are directories compared with `expectFilesMatchGolden`. The test file also parses every IR fixture's output with Python's `ast` (it uses `SQLALCHEMY_PYTHON`, or `python3`, and skips without Python).

The Doctrine tests (`doctrine-emitter.test.ts`) lint the generated PHP with `php -l` and skip when PHP is missing. Set `DOCTRINE_DIR` to a directory where `composer require doctrine/orm symfony/cache` has been run (outside this repository) to also load the entities with Doctrine's real metadata factory, validate the mapping and create the schema in SQLite (`test/tools/validate-doctrine.php`).

The Laravel tests (`laravel-parser.test.ts`) lint the fixture project with `php -l` and skip when PHP is missing. Set `LARAVEL_DIR` to a directory where `composer require illuminate/database illuminate/events illuminate/container` has been run (outside this repository) to also run the fixture migrations in order against SQLite with the real Illuminate packages (`test/tools/replay-laravel-migrations.php`) and compare the resulting tables, keys and indexes with the parser's result.

The GORM tests (`gorm-emitter.test.ts`) run `gofmt -l` over every generated file (all five canonical conversions in both naming modes and all four providers, plus a kitchen-sink and a stress schema from `gormFixtures.ts`) and skip when Go is missing. When the Go modules can be fetched (the tests create a scratch module and `go get` pinned versions of `gorm.io/gorm`, `github.com/glebarez/sqlite`, `github.com/google/uuid`, `github.com/shopspring/decimal`, `gorm.io/datatypes` and the PostgreSQL, MySQL and SQL Server drivers; without network access these tests are skipped), they also `go vet` the models, run `AutoMigrate` on in-memory SQLite and compare the resulting tables, columns, foreign keys and indexes with the IR (`tools/validate-gorm.go`), run persistence checks on the Django blog schema (`tools/validate-gorm-blog.go`: `BeforeCreate` UUIDs, defaults, preloads, unique and referential actions), render the DDL for PostgreSQL, MySQL and SQL Server without a database, and compare the ported column and table naming functions with GORM's own `NamingStrategy`.

The SQLAlchemy parser has its own unit tests (`sqlalchemy-parser.test.ts`: every construct in both styles, the three canonical fixtures giving one schema, hostile and huge input) and fixtures: `fixtures/sqlalchemy/blog/` is the canonical blog schema as a multi-file SQLAlchemy 2.0 package (the canonical fixture), `fixtures/sqlalchemy-sqlmodel/` and `fixtures/sqlalchemy-classic/` the same schema as SQLModel and as classic `Column()` models (the parser test asserts that all three read to the same schema), and `fixtures/sqlalchemy-extras/` the less common constructs. The sqlalchemy format is read-only until the emitter lands, so its goldens are the `sqlalchemy-to-<format>` conversions.

The Django, Graphene, TypeORM and Drizzle tests (`django-verify.test.ts`, `graphene-verify.test.ts`, `typeorm-verify.test.ts`, `drizzle-verify.test.ts`) load the emitted code with the real tools and compare what the tools report with the IR of the canonical blog schema read from every other readable format, plus the larger prisma, django and gorm "extras" fixtures (Graphene covers the canonical Django fixture too) (`realToolSupport.ts` lists them and builds the expected "spec" from the IR). They are skipped with a reason in the test title when the tool is missing, and the `check` CI job does not install them (see "In CI" below). `test/tools/setup-verification-tools.sh [directory]` installs everything into a scratch directory and prints the `export` lines below. The Drizzle parser is checked the other way round (`drizzle-parser-verify.test.ts`): the fixtures are type-checked against `drizzle-orm` and compared with the snapshot `drizzle-kit generate` builds from them.

- Django (`test/tools/validate-django.py`): set `DJANGO_PYTHON` to a Python with Django installed (default `python3`, which is used when it has Django). The script puts `models.py` into a scratch app and runs `check`, `makemigrations --dry-run`, `makemigrations`, `sqlmigrate` and `migrate` on in-memory SQLite, then compares `_meta` (table, column, field type, nullability, uniqueness, lengths, enum choices, relation targets, `on_delete`, `related_name`) and the introspected database (columns, nullability, primary key, foreign keys, unique constraints, named indexes, many-to-many join tables) with the IR.
- SQLAlchemy and SQLModel (parser; `test/sqlalchemy-parser-verify.test.ts`, `test/tools/validate-sqlalchemy.py`): set `SQLALCHEMY_PYTHON` to a Python with SQLAlchemy 2 installed (and `sqlmodel` for the SQLModel fixture); `test/tools/setup-verification-tools.sh` adds both to the Django virtual environment. The canonical blog schema as a SQLAlchemy 2.0 package, in the classic `Column()` style and as SQLModel, and the extras fixture `fixtures/sqlalchemy-extras/shop.py`, are imported with the real libraries, `configure_mappers()` resolves every relationship, every table is created in in-memory SQLite and read back with `inspect(engine)`, and the result is compared with what the parser read: tables, columns (nullability, types, string lengths, decimal precision, enum values), primary keys, foreign keys with their `ON DELETE` / `ON UPDATE` actions, composite foreign keys, unique constraints and indexes (also by name), defaults and `onupdate`, the relationships of the mappers (target, one-to-one versus list, the reverse side named by the parser) and the many-to-many pairs. One row is then inserted into every table that can be filled (foreign keys follow the rows already inserted) and the defaults the parser reported are compared with the values SQLite stored. `fixtures/sqlalchemy-extras/postgres.py` (arrays, ranges, `JSONB`, a schema) cannot be created in SQLite and is only read by the parser tests. Skipped with a reason in the test title when the Python or the packages are missing; the `real-tools` CI job installs them.
- Graphene (`test/tools/validate-graphene.py`): the same `DJANGO_PYTHON`, with graphene-django installed. The generated `schema.py` is imported next to the Django models generated from the same source (a Django source is its own models file, used as written: the project installs `django.contrib.auth` so `settings.AUTH_USER_MODEL` is `auth.User`, and `User = get_user_model()` is appended so the `User` the schema imports from `.models` resolves), `graphene.Schema` is built, its SDL printed and the introspection query run; the script checks the object type and every field and relation of each model, the enum types behind enum fields, the `Query` single and list fields and the `Create`/`Update`/`Delete` mutations, creates the tables, runs every list query and a create, get, update and delete round trip through GraphQL for every model that can be created (a model whose input needs another row, such as a post with its author and category, follows the models it points at; the test for the Django fixture asserts that `Post` and `Profile` go through it).
- Drizzle (`test/tools/validate-drizzle.ts`, `test/tools/validate-drizzle-blog.ts`): set `DRIZZLE_DIR` to a directory where `npm install drizzle-orm drizzle-kit typescript @types/node better-sqlite3 @types/better-sqlite3` has been run. For each schema (the canonical blog schema from every readable format, the prisma, django and gorm extras, and the IR fixtures in `drizzleFixtures.ts`: the GORM kitchen sink and stress schemas plus a `constructs` schema with reference cycles, a self reference, a key that is a relation, a reference to a unique column, array, enum, range, hstore and duration columns and names that collide with Drizzle's exports) in both naming modes, the PostgreSQL, MySQL and SQLite output is compiled together with `tsc --strict`, `drizzle-kit generate` runs for each dialect (no database server is needed) and its snapshot is compared with the IR (tables, columns, nullability, primary keys, unique constraints, indexes, foreign keys and `ON DELETE` actions, string lengths, decimal precision and enums), `extractTablesRelationalConfig` builds Drizzle's relational configuration (it throws for a relation it cannot pair, and both sides of every foreign key must exist), `drizzle-kit push` creates a SQLite file whose tables, columns, foreign keys and indexes are compared again through `PRAGMA`, and a relational query over every relation runs through `drizzle-orm/better-sqlite3`. The Django blog schema is also run against that database: inserts, defaults (`$defaultFn` UUIDs, `unixepoch()`, enum, JSON and boolean defaults), `$onUpdate`, uniqueness, `ON DELETE` actions and the relational query API.
- Zod (`test/tools/validate-zod.ts`): set `ZOD_DIR` to a directory where `npm install zod@4 zod3@npm:zod@3 typescript tsx @types/node` (`test/tools/setup-verification-tools.sh` pins the versions: `zod@4.6.4` and `zod3@npm:zod@3.25.76`, Zod 3 under the alias `zod3`) has been run. The emitted `schemas.ts` is compiled with `tsc --strict`, then the validator (run with `tsx`) builds a valid sample row for every model from the IR and checks that `<Model>Schema`, the create, update and `WithRelations` schemas accept it and reject rows with a missing required property, a too long string, a value outside an enum, a malformed decimal or uuid, a fraction in an integer and null in a required property (null in a required date column is skipped for the default `z.coerce.date()`, which accepts it). Both naming modes and every readable fixture are covered, and the `dates: 'string'` / `bigints: 'bigint'` modes run on the Prisma and django-extras schemas.
- Zod reader (`test/zod-parser-verify.test.ts`, `test/tools/inspect-zod.mjs`): the same `ZOD_DIR`, with both `zod` (4.x) and `zod3` (3.25.x) installed. The fixture modules (`test/fixtures/zod`, `test/fixtures/zod-extras`) and the Zod writer's own output for the canonical Prisma schema are run with the real library through `tsx`, once for each version (the Zod 3 run uses the same source with `from 'zod'` rewritten to `from 'zod3'`). `inspect-zod.mjs` prints what Zod reports about every exported schema: the keys of `schema.shape` in order, `isOptional()`, `isNullable()`, whether a default is set, and the type under the wrappers from `_def.typeName` and `_def.checks` (Zod 3) or `_zod.def` (Zod 4). The test works out the expected columns from those facts alone and compares them with what `parseZod` read: types, array depth, string lengths, decimal precision, enum members, nullability, relations and the key order. Zod's own answers for `z.coerce.*` and json types (they accept `null` or `undefined`) are not compared; `z.stringbool()` is read as the boolean it produces. The test skips with a reason when `ZOD_DIR` is not set or lacks a package.
- TypeORM (`test/tools/validate-typeorm.ts`): set `TYPEORM_DIR` to a directory where `npm install typeorm reflect-metadata better-sqlite3 typescript @types/node` has been run (add `pg mysql2 mssql` to also build the PostgreSQL, MySQL and SQL Server entities). The entities of every provider are compiled with `tsc` (`experimentalDecorators`, `emitDecoratorMetadata`, strict), TypeORM's metadata is built for them (`DataSource.buildMetadatas`, which rejects column types the driver does not support) and compared with the IR in both naming modes; the SQLite entities are also synchronized into an in-memory database (`synchronize: true`) and its tables, columns, foreign keys, unique constraints and indexes are compared. Without a server, PostgreSQL, MySQL and SQL Server only get the compile and metadata checks.
- JSON Schema (`test/json-schema-verify.test.ts`): set `AJV_DIR` to a directory where `npm install ajv ajv-formats` has been run. The emitted document is loaded with the draft 2020-12 build of Ajv in strict mode (`validateSchema`, then every `$defs` entry is compiled so each `$ref` resolves); sample rows built from the IR must validate, and rows with a missing required property, a null in a non-nullable column, a too-long string, a value outside an enum, a malformed date-time or an unknown property must be rejected. Runs in-process (no subprocess), for every canonical and extras source.

The EF Core emitter tests are in `efcore-emitter.test.ts` (layout and both styles, names, every column type and provider, keys, defaults, enums, indexes, relations, many-to-many, timestamps, warnings, reading the output back with the parser, and the goldens `golden/*-to-efcore.*`, `golden-extras/efcore-fluent`, `efcore-fixtures` and `efcore-providers`; `efcoreFixtures.ts` is the IR fixture with the shapes that need special handling). The parser's unit tests are in `efcore-parser.test.ts` (entity discovery, every data annotation and fluent call, conventions, relationships, inheritance, warnings, hostile input, directory input and the extras goldens `golden-extras/efcore-*`). The canonical blog schema is `fixtures/efcore/` (annotated entities, an `IEntityTypeConfiguration<Post>` and a `DbContext`) and is a source of the conversion matrix; `fixtures/efcore-extras/` has `shop` (conventions, the fluent API, owned types, a composite key, skip navigations, computed columns), `inheritance` (table per hierarchy) and `library` (data annotations and delete behaviors). Each group is one `DbContext` that the real EF Core can load.

The Hibernate / JPA format is read and written. The writer's unit tests are in `jpa-emitter.test.ts` (layout and options, styles, every column type and provider, defaults, enums and converters, keys, relations, indexes, warnings, reading the output back, and the goldens `golden/*-to-jpa.*`, `golden-extras/jpa-javax` and `golden-extras/jpa-fixtures`, in `jpa-emitter-golden.test.ts`); the IR fixture is `jpaFixtures.ts`. The two options that change the Java (`--jpa-key embedded` for `@Embeddable` keys with `@EmbeddedId`, and `--lombok`) have their unit tests in `jpa-embedded-lombok.test.ts` (including reading the output back as the same key) and their goldens in `jpa-modes-golden.test.ts` (`golden-extras/jpa-modes`); the default output keeps its goldens untouched. The parser's unit tests are in `jpa-parser.test.ts` (entity discovery, `jakarta` and `javax` annotations, every column type, nullability and length precedence, defaults, enums, converters, relationships, join tables, composite keys, embeddables, the inheritance strategies, element collections, indexes, constructs that are reported, hostile input), and `jpa-fixtures.test.ts` covers the canonical fixture, directory input (what is skipped) and the extras goldens `golden-extras/jpa-*`. The Sequelize format is read and written. The parser's unit tests are in `sequelize-parser.test.ts` (every model style and option with small inline sources, warnings, errors, file filtering, hostile input, the canonical fixture and the extras goldens `golden-extras/sequelize-*`). The writer's are in `sequelize-emitter.test.ts`: every feature in both styles (`init` and `define`), both naming modes and every provider, the warnings, hostile names, the output read back with the parser (the Sequelize fixtures come back unchanged), and goldens. The default (`init` style) conversions of every readable format are the directories `golden/<format>-to-sequelize.<naming>/` like any multi-file format. The `define` style of every canonical schema is `golden-extras/sequelize-define/<format>-to-sequelize/{preserve,normalize}/` (with the warnings), and `golden-extras/sequelize-fixtures/<fixture>/` holds both styles and naming modes of the prisma, django and gorm extras, the kitchen-sink, stress and constructs IR fixtures and the Sequelize fixtures, with the warnings and `init.preserve.drift.txt` (what the parser makes of the output); `golden-extras/sequelize-providers/constructs/` the constructs fixture for every provider. The canonical blog schema is `fixtures/sequelize/models/` (the layout `sequelize-cli` generates; its `package.json` marks the CommonJS files as such inside this ES module package) and is the Sequelize source of the conversion matrix; `fixtures/sequelize-extras/` holds the variants (`variants.js`: plural, underscored and paranoid tables, custom timestamps, join models, key options, composite uniques and indexes), a TypeScript `Model.init` class file and a sequelize-typescript file.

Sequelize migrations are replayed by the same parser (`sequelize-migrations.test.ts`): `fixtures/sequelize-migrations/<set>/` holds folders of `sequelize-cli` migrations (`blog`: a blog built up over six migrations; `shapes`: module shapes, column types and transactions; `keys`: constraints; `changes`: rename, change and drop; `typescript`: `.ts` migrations), `sequelizeMigrationCases.ts` one small case per `queryInterface` call and migration shape, and the goldens `golden-extras/sequelize-migrations/*.txt` summarize the schema and the warnings of each (`schemaSummary.ts`; the files are handed over in reverse order, because the replay sorts them by name). The same file tests how `--from sequelize` finds migrations (a folder on its own, a project without models, `.sequelizerc`, a project that has both). Sequelize 7 has `sequelize7-parser.test.ts` (the canonical blog schema in decorators, `fixtures/sequelize7/models/`, reads to exactly the IR of the Sequelize 6 fixture; `fixtures/sequelize7-extras/variants.ts` and its golden `golden-extras/sequelize7/variants.txt`; the differences between the generations) and `sequelize7-emitter.test.ts` (`--style v7`: layout, decorators, SQLite types, relations, the goldens `golden-extras/sequelize7-fixtures/<fixture>/{preserve,normalize}` with the warnings and `preserve.drift.txt`, `golden-extras/sequelize7-providers/constructs`).

- Sequelize (`sequelize-parser-verify.test.ts`, `test/tools/validate-sequelize.mjs`): set `SEQUELIZE_DIR` to a directory where `npm install sequelize@6 sqlite3` has been run (Sequelize does not support `better-sqlite3`; add `sequelize-typescript reflect-metadata typescript @types/node` for the two TypeScript fixtures, which are compiled with `tsc` first and skipped with a message when those packages are missing). Each fixture is loaded in a Node subprocess, `sequelize.sync()` creates the tables in in-memory SQLite, and the script prints what `queryInterface.describeTable` and the SQLite `PRAGMA`s report (columns, nullability, primary keys, unique and plain indexes, foreign keys with their actions). The test compares that with the parsed IR: tables (the join tables of string `through` associations are matched to the many-to-many relations), columns, nullability, primary and unique keys, indexes and foreign keys (target column and `ON DELETE`; `ON UPDATE` only when the IR records one, because `CASCADE` is left out as the default).
- Sequelize migrations (`sequelize-migration-verify.test.ts`, `test/tools/validate-sequelize-migrations.mjs`; `SEQUELIZE_DIR` with `sequelize-cli` added to the packages above, and `typescript @types/node` for the TypeScript set): each folder of `fixtures/sequelize-migrations` is copied to a temporary directory and run with the real `sequelize-cli db:migrate` against a SQLite file, `sequelize-cli` sorting and loading the files as a project would. The script prints what the database holds (the `queryInterface.describeTable` view with column types and defaults, and the SQLite `PRAGMA`s), and the test compares that with the replay of the same files: tables, columns, types (`VARCHAR(n)`, `DECIMAL(p,s)`, `TINYINT(1)` for booleans, ...), defaults, nullability, primary and unique keys, indexes, and foreign keys with their actions. Each set is also replayed without one migration that changes the schema, which has to differ from the database (so the comparison can fail). SQLite rebuilds a table for `renameColumn`, `changeColumn` and `removeColumn` and loses foreign key actions and unique keys when it does, so the sets use those calls only on tables without keys; the unit tests replay them everywhere.
- Sequelize 7 (`sequelize7-parser-verify.test.ts`, `sequelize7-verify.test.ts`, `sequelize7Support.ts`, `test/tools/validate-sequelize7.mjs`): set `SEQUELIZE7_DIR` to a directory where `npm install @sequelize/core @sequelize/sqlite3 typescript @types/node` has been run (the setup script pins the alpha release it was written against, 7.0.0-alpha.48). The reader's fixtures (`fixtures/sequelize7`, `fixtures/sequelize7-extras`) and the writer's output (the canonical blog schema of every format, the extras and two IR fixtures, both naming modes, written for SQLite) are compiled with `tsc --strict` against the types of `@sequelize/core`, loaded in a Node subprocess with `new Sequelize({ dialect: SqliteDialect, models })`, and `sequelize.sync()` creates the tables in a SQLite file that the script reads back with the PRAGMAs. The comparison with the IR is the one of the Sequelize 6 tests (`sequelizeSupport.ts`), and every relation of the IR has to be an association of the loaded models under its alias. The v7 SQLite dialect has no `DECIMAL` or `BIGINT`, so the reader fixtures are loaded with `DOUBLE` and `INTEGER` in their place (the parser reads the same text, so the IR still matches).
- Sequelize writer (`sequelize-verify.test.ts`, `test/tools/validate-sequelize-emitter.mjs`, `test/tools/generate-sequelize-sql.mjs`; the same `SEQUELIZE_DIR`, and `typescript @types/node` for the type check, `pg pg-hstore mysql2 tedious` for the dialect SQL): the models are written for SQLite in both styles and naming modes for the canonical blog schema of every format, the prisma, django and gorm extras and two IR fixtures (the kitchen-sink and stress schemas of `gormFixtures.ts`; SQLite cannot evaluate a PostgreSQL `dbgenerated` default, so those are left out of the schema that is written). The TypeScript is transpiled, `initModels(sequelize)` defines and associates the models, `sequelize.sync()` creates the tables, and the script reads them back (the comparison with the IR is the one of the parser test, `sequelizeSupport.ts`) and inserts sample rows through the models: it checks that a generated row carries the defaults of the IR, that every foreign key refuses a missing parent and does what `ON DELETE` says (cascade, set null, refuse), that a single-column unique key rejects a duplicate, that a value outside an `ENUM` is rejected, and that every association works (`include` for `belongsTo`, `hasMany` and `hasOne`, `add` and `count` for `belongsToMany`) under the alias the IR names. A second test type-checks the `init` output of two schemas with `tsc --strict`, and a third generates the `CREATE TABLE` statements Sequelize builds for PostgreSQL, MySQL and SQL Server (no server is needed; the drivers only have to be installed) and looks for the types, enums, defaults and keys of each dialect.
- Entity Framework Core (`efcore-parser-verify.test.ts`, `efcore-emitter-verify.test.ts`, `efcoreSupport.ts`, `efcoreBehavior.ts`, the project `test/tools/efcore-verify`): needs the .NET SDK (8 or later; `dotnet` on the PATH, or `DOTNET` naming the executable) and `EFCORE_DIR`, a scratch directory that holds the NuGet cache and the home of the dotnet CLI (`test/tools/setup-verification-tools.sh` fills it, and installs the SDK with `dotnet-install.sh` when none is found; without a populated cache the first run restores `Microsoft.EntityFrameworkCore.Sqlite` 8 and `Npgsql.EntityFrameworkCore.PostgreSQL` 8 from nuget.org). The test copies the tool project to a temporary directory, compiles every C# fixture (`fixtures/efcore` and `fixtures/efcore-extras/*`, each in its own namespace) with it, creates each `DbContext` in in-memory SQLite with `EnsureCreated()` and prints the `PRAGMA` view of the tables as JSON. The parser's schema for the same C# files is compared with that: tables, columns, nullability, primary keys (also composite), unique keys, indexes (EF Core's implicit index on every foreign key is ignored), foreign keys with their delete actions, and the join tables of the many-to-many relations. SQLite hides lengths and precision, so those are not compared. `efcore-emitter-verify.test.ts` does the same for the writer: the output for every canonical schema, the extras, the EF Core fixtures and three IR fixtures (both styles and both naming modes, written for SQLite) is compiled into one assembly with `-p:Strict=true` (warnings are errors and the implicit usings are off, so a missing `using` or an unchecked nullable fails), each `AppDbContext` creates its SQLite database and `compareWithDatabase` compares it with the IR (composite foreign keys included); with `--exercise` the tool then saves one row into every table through the entity classes and `efcoreBehavior.ts` compares the defaults in the DDL, the enum values stored, the generated keys and the columns the `SaveChanges` override refreshes. The PostgreSQL output of every schema is compiled too (against the Npgsql provider, not run). Skipped, with the reason in the test title, when `EFCORE_DIR` is not set or the SDK is missing.

## In CI

`.github/workflows/ci.yml` has a `check` job and seven `real-tools-*` jobs that run in parallel, plus a final `real-tools` job.

`check` (lint, format, build, `npm test`) installs no tools, so the optional tests skip there and it stays fast. It also runs every test file that needs no tool, and `gorm-emitter` and `gorm-verify`, because it installs Go with `actions/setup-go` (the runner image happens to ship Go, but the GORM tests skip themselves without it, so the install makes sure they always run; there is no separate Go job). Each `real-tools-*` job installs the tools of one ecosystem and runs only the test files that use them (`npx vitest run <files>`), so nothing skips. They share `test/tools/setup-verification-tools.sh`, which takes component names (`python`, `typeorm`, `ajv`, `drizzle`, `sequelize`, `zod`, `sql`, `node` for all the npm tools, `prisma`, `dotnet`, `java`) after the directory and then installs and prints the `export` lines of those only; with no component it installs everything, as before.

`real-tools` waits for all seven (`needs`, `if: always()`) and fails when any of them failed, was cancelled or did not run, so it is the one name to require in branch protection, and `publish.yml` still calls this workflow with `needs: ci`. The file names above are `test/<name>.test.ts`. npm, pip, Composer, Go module, NuGet and Maven downloads are cached per job. Each job has its own `timeout-minutes` (5 to 10, about twice its duration on a cold cache), so a hung test step fails fast, and re-running the failed jobs repeats only that ecosystem.

## Publishing a release (what the Publish workflow runs)

`.github/workflows/publish.yml` runs on a `v*.*.*` tag. The tag points at the merge commit on `main`, and `ci.yml` already ran on the `push` to `main` for exactly that commit, so the workflow reuses that result instead of running every job again (the whole suite takes about 4 to 5 minutes, and the Publish run used to take about 9 minutes because it ran it a second time).

A `gate` job runs `.github/scripts/find-green-ci.sh "$GITHUB_SHA"`. It asks the GitHub API (with the job's `GITHUB_TOKEN`, which has `actions: read` there and nothing else) for the runs of `ci.yml` whose head commit is the tagged commit and whose event is `push`; `pull_request` runs are never counted, because they test a merge ref, not this commit.

| Push CI run of the tagged commit                                                  | Gate output   | What happens                                                                                     |
| --------------------------------------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------ |
| Completed, `success`, and its `check` and `real-tools` jobs both `success`        | `reuse=true`  | The `ci` job is skipped and `publish` runs (after its own tag, `main` ancestor and build checks) |
| Queued or in progress                                                             | waits         | Polls every 30 s for up to 25 minutes, then decides as in this table with what it finds          |
| Failed, cancelled, timed out, skipped, or green but with a skipped or missing job | `reuse=false` | The `ci` job runs the whole suite again; `publish` runs only if it succeeds                      |
| None (for example a tag pushed to a commit that never went through `main`)        | `reuse=false` | Same: the whole suite runs again (it looks for 60 s first, in case the tag beat the push run)    |
| The API cannot be read, or the answer cannot be parsed                            | `reuse=false` | Same                                                                                             |

`publish` has `if: always() && ...` with explicit result checks: it runs only when the gate succeeded and either (`reuse=true` and `ci` was skipped) or (`reuse` is not true and `ci` succeeded). A failed or cancelled `ci`, a failed gate, or a skipped `ci` without reuse never publishes (`test/publish-workflow.test.ts` evaluates the conditions for every combination). The tag-matches-`package.json`, commit-is-on-`main`, provenance and dist-tag steps are unchanged.

Re-running and forcing a full run: re-running the Publish workflow (or its failed jobs) asks the gate again, so nothing has to be deleted or changed. If the push run was red, fix the cause and re-run that CI run on `main` (or let Publish run its own: with no green push run it runs the whole suite itself, which is the old behavior). If you want a fresh full run of the suite before publishing anyway, re-run the `push` CI run of the commit on `main` (Actions, CI, Re-run all jobs): while it runs the gate sees it as in progress and waits for its new result. To try the lookup yourself: `GITHUB_REPOSITORY=RichardMcQuiston01/ormbridge GH_TOKEN=... .github/scripts/find-green-ci.sh <sha>` (it needs `gh` and `jq`); `test/find-green-ci.test.ts` runs it against a fake `gh`.

## Conversion matrix

`conversion-matrix.test.ts` adds a semantic layer on top of the text goldens: for every ordered pair of readable and writable formats it reads A's fixture, writes B, reads B back and compares the two IRs with `irCompare.ts`. New readable formats join automatically. Write-only formats with a structural check (`EMIT_ONLY_CHECKS` in `conversionMatrix.ts`, currently GORM, Drizzle, JSON Schema, Zod, SQL DDL and SQLAlchemy) get a "Write-only targets" section instead of IR comparisons, with their approximations in `EMIT_ONLY_NOTES`. Every difference must be explained in `conversionMatrixDoc.ts` (`LOSS_REASONS`), and `docs/CONVERSION_MATRIX.md` is generated from the results (`npm run docs:matrix`, or `UPDATE_GOLDEN=1 npm test`).

## Round-trip drift files

`roundtrip-<from>-<via>.drift.txt` lists what a round trip changes. An empty file means the pair is lossless for the fixture. A non-empty file documents a lossy mapping: `+` lines were added and `-` lines were lost. Any change to a mapping shows up as a diff in these files.

`examples.test.ts` runs `ormbridge convert --check` in every folder of `examples/` (one per registered format, each with a config file and README), so a change to an emitter or parser that alters the committed example output fails until `npm run examples` regenerates it.
