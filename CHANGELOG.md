# CHANGELOG

## Unreleased

## 0.16.0 - 2026-10-30

The Sequelize 7 output is now verified against real PostgreSQL 16 and MySQL 8 servers, and the fixes that checking showed are in the writer. **Output change:** `--to sequelize` writes the PostgreSQL operator class `jsonb_path_ops` for Prisma's `JsonbPathOps` and `[]` for the default of an array of enum values, and, for MySQL, `DECIMAL(10, 0)` for a `DECIMAL` without precision and no index over a JSON or array column, no model schema and no index method other than `BTREE` or `HASH` (each with a warning); every other conversion is unchanged.

The Sequelize 7 output and fixtures are now run against real PostgreSQL 16 and MySQL 8 servers, not only SQLite. **Output change:** a few small fixes to `--to sequelize` that the real servers showed (below); every other conversion, and every existing golden file except the `prisma-extras` and `django-extras` Sequelize ones (`golden-extras/sequelize-fixtures/`, `sequelize7-fixtures/`), is unchanged. SQL Server stays on the roadmap.

### Added

- `test/sequelize7-server-verify.test.ts` and `test/tools/validate-sequelize7-server.mjs`: the models `--style v7 --provider postgresql` / `mysql` writes (the canonical blog schema of every format, the extras, the kitchen-sink and stress fixtures and a `BIGINT` / `DECIMAL` schema, both naming modes) and the Sequelize 7 reader fixtures are compiled with `tsc --strict`, defined with the real `@sequelize/core` and synced into a scratch database of the server. The tables, columns, types (real `BIGINT` and `DECIMAL(p,s)`), nullability, defaults, keys, indexes and foreign keys with their actions that the catalogs report are compared with the IR. The tests skip with a reason without `SQL_POSTGRES_URL` / `SQL_MYSQL_URL` or the dialect package, and run in the `real-tools-databases` CI job.
- The `sequelize7` component of `test/tools/setup-verification-tools.sh` also installs `@sequelize/postgres` and `@sequelize/mysql`, pinned to the version of `@sequelize/core` (7.0.0-alpha.48).

### Changed

- **Output change** (Sequelize writer, all styles, PostgreSQL): the operator class of an index is written as PostgreSQL names it, `jsonb_path_ops` where `JsonbPathOps` (Prisma's spelling) was written, which PostgreSQL refused (`operator class "jsonbpathops" does not exist`). A `raw("...")` operator class is unwrapped.
- **Output change** (Sequelize writer, all styles): the empty default of an array of enum values is written as `[]` where it was the string `'[]'`, which Sequelize 7 refuses for an array column on PostgreSQL.
- **Output change** (Sequelize writer, `--provider mysql`): a `DECIMAL` without precision is written as `DECIMAL(10, 0)` with a warning in `--style v7` (the Sequelize 7 MySQL dialect throws on the bare type); a model `schema` is ignored with a warning (MySQL would take it for another database); `using` other than `BTREE` and `HASH` (`GIN`, ...) is dropped with a warning; and an index over a JSON column, or an array column (written as JSON), is skipped with a warning because MySQL refuses it.

## 0.15.0 - 2026-10-21

Two more migration readers and a new Sequelize generation: EF Core migrations are replayed (with `OwnsMany`), and `sequelize-cli` migrations are replayed while Sequelize 7 is read and written. **Output change:** the EF Core reader (`OwnsMany` properties are now models; a directory input also reads `Migrations/`) and the Sequelize reader (a project root with migrations but no models is converted; `uuidv4`/`uuidV1` defaults are read as UUID defaults; the `--style` error text and the `formats` line list the new styles); every other conversion is unchanged.

EF Core migrations can be read and `OwnsMany` is supported. `--from efcore` on a folder of migrations without entity classes replays the `Up` methods in migration order into one schema (a `*ModelSnapshot.cs` that agrees supplies the entity and property names), and an owned collection (`OwnsMany`) is a child model with a foreign key to its owner. **Output change:** `OwnsMany` properties used to be skipped with a warning and are now models; `--from efcore` on a directory now also passes the `Migrations` folder and the snapshot to the reader, which skips them with one warning when the input has entity classes and replays them when it has none (such input used to fail with `NO_MODELS_FOUND`).

The Sequelize gaps are closed: `sequelize-cli` migrations are replayed, and Sequelize 7 (`@sequelize/core`) is read and written. **Output change:** none for existing conversions, except for the `--style` error message and the `ormbridge formats` line of `sequelize` (they list the new styles), the reading of a few defaults in Sequelize files (below), and the Sequelize reader now reading a project root that has migrations but no model files, which used to fail with `NO_INPUT_FILES`. Every existing golden file passes untouched.

## 0.14.0 - 2026-10-21

Three reader and writer gaps are closed: SQL migrations are replayed completely, Zod schemas can be read, and JPA writes `@EmbeddedId` keys and Lombok accessors. **Output change:** the SQL reader (applied `ALTER`/`RENAME`/`DROP` statements, MySQL unique indexes, MySQL join tables, directory file order) and the JPA reader (`@EmbeddedId` attribute names); every other conversion is unchanged.

The SQL reader now replays migrations completely. A folder of `.sql` migrations (Flyway, drizzle-kit, Prisma, Liquibase formatted SQL or plain numbered files) is read as the schema the database ends with. **Output change:** `ALTER TABLE` statements that used to be skipped with a warning (renames, dropped columns, type changes, dropped constraints and indexes, `RENAME TABLE`, `DROP INDEX`) are now applied, so the schema read from such input changes, and the warnings `Skipped N ALTER TABLE ... DROP / RENAME / ALTER COLUMN statements` are gone. A MySQL join table that a dump lists with its foreign-key indexes is now read as a many-to-many field, like the other dialects. Nothing else changes for input without those statements.

Two gaps of the Hibernate / JPA format are closed: composite primary keys can be written as `@Embeddable` classes with `@EmbeddedId`, and Lombok accessors are a separate option. The default output does not change.

Zod becomes a readable format: `--from zod` reads Zod 3 and Zod 4 modules into the shared model, so `zod` can be both read and written. **Output change:** none for existing conversions; the only changes to files are new goldens and the regenerated conversion matrix.

### Added

- JPA writer: `--jpa-key embedded` (config key `jpaKey`, `emitJpa` option `keyMode`, `convertText` option `jpaKey`; values `idclass`, the default, and `embedded`). A composite primary key is written as an `@Embeddable` key class (`<Entity>Id`: `Serializable`, a `@Column` on every part, constructors, accessors, `equals`, `hashCode`) and one `@EmbeddedId` attribute on the entity; a relation that is part of the key keeps its attribute and gets `@MapsId("<attribute>")`, and the key class repeats its foreign key column. Keys of one column stay a plain `@Id`. It works with both styles and both naming modes. `JPA_KEY_MODES`, `isJpaKeyMode` and the `JpaKeyMode` type are exported.
- JPA writer: `--lombok` (config key `lombok`, `emitJpa` and `convertText` option `lombok`). Entities get `@Getter`, `@Setter` and `@NoArgsConstructor` instead of accessors; key classes get `@NoArgsConstructor`, `@AllArgsConstructor` and `@EqualsAndHashCode` (an `@Embeddable` key class also `@Getter` and `@Setter`) instead of constructors, `equals` and `hashCode`. It works with `jakarta` and `javax`, and with both key modes. The options were not added as `--style` values, because a style picks one value of one axis (`jakarta` or `javax`) and these two combine freely with it and with each other. Other targets ignore both options, as they ignore `--style`.
- JPA reader: an `@Embedded` value object that is flattened into plain columns now gets a warning naming the entity, the attribute and the columns (`Home.address: the embedded Address was flattened into the columns address.street, address.city; ...`), because the shared model has no embedded type and the class is lost. The `@Embeddable` of an `@EmbeddedId` gets none.
- Verification with the real tools: `test/jpa-emitter-verify.test.ts` also writes every schema with embedded keys and Lombok (both together in both styles and both naming modes; each option alone in one) and compiles it with Lombok 1.18.32 as an annotation processor (`pom-javax.xml` now has Lombok too). Hibernate 6.4 and 5.6 create the schema in H2 and it is compared with the IR; `Exercise.java` builds the `@EmbeddedId` value (taking the parts that a `@MapsId` relation supplies from the saved target), saves a row, loads it again by its key object and checks that the key reported by Hibernate is equal to the one saved (`equals` and `hashCode`, also Lombok's). The tests skip with a reason when Java or Maven is missing. The `real-tools-java` job is unchanged.
- Tests and fixtures: `jpa-embedded-lombok.test.ts` (unit tests, reading the output back as the same key), `jpa-modes-golden.test.ts` and `test/golden-extras/jpa-modes` (goldens of both options for four fixtures, with what reading the output back changes), the fixture `test/fixtures/jpa-extras/embedded-keys` (an `@EmbeddedId` with Lombok, `@MapsId` and `@AttributeOverride`), reader tests for `@IdClass` and `@EmbeddedId` as the same key, and CLI and config tests for the new options.
- Docs: `docs/formats/jpa.md` (embedded keys, Lombok, value objects), `docs/CLI.md`, `docs/FIELD_MAPPING.md`, `docs/LIMITATIONS.md`, `README.md`, `ROADMAP.md` (both items done; inheritance, `@Version`, a Kotlin / Spring Data flavour, JSON for Hibernate 5 and `orm.xml` remain) and `test/README.md`.
- Zod reader: `--from zod` (`src/parsers/zod.ts`, `zodFields.ts`, `zodSyntax.ts`; `parseZod`, `ZodSourceFile` and `ZodParseOptions` are exported). The `zod` format is now `read + write`; it still claims no extension, so `.ts` stays unclaimed and a folder needs `--from zod` (it reads `.ts`, `.mts`, `.js` and `.mjs` files and skips `node_modules/`, `*.d.ts`, `*.test.*` and `*.spec.*`). The files are read with tree-sitter and never run. Every top-level `z.object({ ... })` bound to a variable is a model, named after the variable without `Schema` (`UserSchema` gives `User`), with the property order kept.
- Types: strings (`.max(n)` / `.length(n)` give a length, otherwise `text`), the Zod 3 and Zod 4 string formats (`.uuid()` and `z.uuid()`, IP addresses, base64, ISO dates, times and durations; other formats such as `email` stay plain strings), numbers (`.int()`, `z.int()`), `bigint`, dates, `z.coerce.*`, enums (`z.enum` over an array, a const array or a const object, `z.nativeEnum` over a TypeScript enum, a union of string literals), arrays, `z.record` / `z.any` / `z.unknown` / `z.json` as json, and the decimal and big-integer patterns the Zod writer produces (read back with their precision). `.optional()`, `.nullable()` and `.nullish()` make a column nullable; `.default()`, `.catch()` and `.prefault()` are read as a default when it is a literal, an enum value, `() => new Date()`, `crypto.randomUUID()` or an empty object or list.
- Building schemas: `.extend`, `.merge`, `.pick`, `.omit`, `.partial`, `.required`, `...Other.shape` and a spread of a plain object of properties are resolved when the base schema is in the input (also in another input file), named schemas and shared property objects are followed, and Zod 4 getters and `z.lazy` are read. The create, update and with-relations schemas that `--to zod` writes are skipped.

[SET DATA] TYPE ... USING`, MySQL `MODIFY`, SQL Server `ALTER COLUMN`), `SET` / `DROP NOT NULL`, `SET` / `DROP DEFAULT`, `DROP IDENTITY`, `DROP EXPRESSION`, `DROP CONSTRAINT`, `DROP PRIMARY KEY`, `DROP FOREIGN KEY`, `DROP CHECK`, `DROP INDEX` (all four forms, CockroachDB `table@index`), `RENAME CONSTRAINT`, `RENAME INDEX`, `ALTER INDEX ... RENAME TO`, CockroachDB `ALTER PRIMARY KEY`, `ALTER TYPE ... RENAME TO / RENAME VALUE`, `DROP TABLE [IF EXISTS] a, b [CASCADE]`, and `CREATE INDEX IF NOT EXISTS`. A rename carries the foreign keys, primary key, unique keys, indexes, `CHECK` enums and generated-column expressions that use the table or column. An unnamed constraint or index can be dropped by the name PostgreSQL or MySQL gives it (`t_a_key`, `t_b_fkey`, `t_c_check`, `t_a_idx`, `t_ibfk_1`), and that name is kept when the table or column is renamed. Dropping a column drops the keys, indexes and checks that use it (MySQL shrinks them), dropping a table with `CASCADE` drops the foreign keys that point at it, and `serial` columns become plain integers when their default or type is touched.
- Warnings that name the file, the line, the statement, the table and the column when a statement does not fit (`m.sql:3: ALTER TABLE "t" RENAME COLUMN "missing": the column does not exist at this point; the statement was skipped.`). Changes that cannot be replayed (`SET SCHEMA`, partitioning, unknown forms) are counted once per kind and name the first table. `INSERT`, `UPDATE`, `DELETE`, `SELECT`, `COPY` and `MERGE` give one summarizing warning for the whole input; `TRUNCATE` is ignored without a warning.
- Reading an ordered set of migration files as one schema (`src/parsers/sqlMigrationOrder.ts`, used by `src/io.ts` for a directory input of `--from sql`): Flyway `V<version>__name.sql` by numeric version (`V2` before `V10`, `V1.2` before `V1.10`), `R__` repeatable files last, `U` undo scripts and callbacks skipped; drizzle-kit `NNNN_name.sql` in the order of `meta/_journal.json` (the `--> statement-breakpoint` lines are comments); everything else in natural file-name order (`2_x.sql` before `10_x.sql`), directory by directory. Liquibase formatted SQL (`--changeset` lines) is read as comments. Files named one by one keep the order given. `orderSqlMigrationFiles` is exported from the package.
- A file with no dialect hint of its own is read with the dialect of the set it belongs to (a MySQL set with an `ALTER TABLE t DROP COLUMN c` file), and backticks alone no longer make a SQLite set MySQL (drizzle-kit writes SQLite with backticks; a tie between SQLite and MySQL evidence now goes to SQLite).
- Tests: `sql-migration-verify.test.ts` runs migration sets (`test/fixtures/sql-migrations/`: PostgreSQL 16 blog, shop and edge sets, MySQL 8 blog, shop and edge sets, a CockroachDB set, a SQLite drizzle-kit set) in real servers, dumps the final schema (`pg_dump --schema-only`, `SHOW CREATE TABLE`, `SHOW CREATE ALL TABLES`, `sqlite_master`) and checks that replaying the files gives exactly the schema the reader finds in the dump (only database-made constraint names and the PostgreSQL cast on a default expression are ignored), and that a replay one migration short differs. `sql-migration-replay.test.ts` has golden summaries of every statement form for each dialect (`test/golden-extras/sql-migration-replay/`, cases in `test/sqlReplayCases.ts`), the file-order rules, and a round trip that writes each fixture schema to SQL in the four dialects, cuts it into one Flyway file per statement and checks that the replay equals the whole script. The CI `real-tools-databases` job runs the new live test with its existing PostgreSQL, MySQL and CockroachDB services (a few seconds; the job timing does not change) and checks for `pg_dump`.
- Docs: "Migrations" in `docs/formats/sql.md`, the drizzle-kit and Flyway notes in `docs/formats/drizzle.md` and `docs/formats/jpa.md`, and updates to the README, `docs/CLI.md`, `docs/FIELD_MAPPING.md`, `docs/LIMITATIONS.md`, `test/README.md`, the conversion matrix and the roadmap (Liquibase XML / YAML and Alembic migrations remain).

### Changed

- **Output change** (JPA reader): the attributes of an `@EmbeddedId` are named like the `@Id` attributes of an `@IdClass`, without the name of the `@EmbeddedId` attribute as a prefix: `sku` where `idSku` was read before, so both forms of a key read back as the same primary key (`compositePrimaryKey: ['sku', 'warehouse']`).
